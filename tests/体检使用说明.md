# 体检使用说明（光明顶 5v5 · 回归与体检）

> **这是什么**：一套独立于游戏本体之外的「自动查病」工具。它不跑浏览器 UI，而是直接调用引擎
> 打大量确定性战斗，再从战斗流水（fact / 日志条目）里逐条核对"该发生的发生了没有、数字对不对、
> 单位状态有没有错乱"。
>
> **为什么需要**：精英角色与跨机制联动的问题（机制互耦、UI 层与引擎层不同步）只有在特定阵容、特定回合
> 才现形，随手抽一局几乎碰不到；体检就是把它变成「可重复、可机器比对」的常态化检查。
>
> **⚠ 本文档的定位（先看这句）**：体检的**正式协议文档是 `文件汇总20260730/README-体检.md`** ——
> 它是根目录 `README.md` 明示的**四大官方专项衍生版之一**（README-IDE / README-工具 / README-体检 /
> README-文件），职责范围、强制规则、工作方式**以它为准**。
>   本文件**不是**那份的改写版，**不取代**它，也不参与那套命名；它只是一份贴在 `tests/` 目录里的

## 一、它由哪几部分组成

| 组成 | 文件 | 干什么 |
|---|---|---|
| 静态快检 | `tests/123static-scan.js` | **不跑游戏**，直接读源码文本查结构病：枚举/共享符号用了却没 import、import 路径断。秒级出结果 |
| 规则回放 | `tests/rules-replay.mjs` | **主力**。真跑引擎 120 场（默认 20 种子 × 6 关），把战斗流水渲染成战报条目，再逐条喂给下面的规则；同时跑「不变量」逐步断言 |
| 规则集 | `tests/health-rules/*.js`（30 条） | 每条规则盯一个具体机制的判据（如九阴白骨爪伤害、坚盾层数上限、长生人员的附身/飞回…）。新增规则必须四方登记 |
| 实时体检监控器 | `tests/121health-monitor.js` | 浏览器侧跑，打完一局就地跑规则；取终局真值（`battleStore`），**不能**吃开战时的旧快照 |
| 工具函数 | `tests/122health-utils.js` | 血量合法性、pos 唯一等公用判据的唯一实现（各规则复用，不各写一份） |
| 规则裁剪集 | `tests/124rule-recipes.js` | 标注每条规则在什么条件下才可能触发，消除海量无意义的 skip 噪音 |
| 确定性基线 | `tests/140-baseline.js` + `tests/baselines/baseline-v1.json` | 6 种子 × 3 关 = 18 场，记录胜者/回合数/fact 序列，供「零行为变化」重构做机器 diff |
| 引擎冒烟 | `tests/smoke-headless.mjs` | 跑 20 局确认引擎本身跑得完、分得出胜负、导出齐全 |
| 登记一致性 | `tests/registration-check.mjs` | 核对 30 条规则在 **121 / 123 / 124 / 106** 四处是否都登记齐全（漏登、重复登记）。tools/106 侧只提示不计失败 |
| 覆盖度报告 | `tests/coverage-report.mjs` | 报出每条规则**实际触发过几次**（120 场里只跑 6 次的规则"通过了"也等于没在测）。零触发 = 空转，退 1 |
| 浏览器入口 | `tests/120test-runner.html` | 手动自检页面（默认从第 2 关起、4 倍速） |

## 二、怎么用（命令速查）

```bash
node tests/123static-scan.js          # 静态快检（106 文件），有 issue 退出码 1
node tests/rules-replay.mjs           # 规则回放 120 场 + 不变量逐步断言
DEAD=1 node tests/rules-replay.mjs    # 严格模式：存在"恒空转规则"就退 1
node tests/140-baseline.js            # 全量重跑 18 场并**重录**基线（业务有意变更后用）
node tests/140-baseline.js --check    # 与基线比对；不一致时二分输出「预期变更/回归」，回归才退 1
node tests/140-baseline.js 42:3       # 只跑 seed=42 stage=3 打印，不写基线
node tests/smoke-headless.mjs         # 引擎冒烟
node tests/registration-check.mjs     # 规则四方登记一致性（tests 侧缺失退 1；tools/106 侧仅提示）
```

五件套常态应同时满足：**静态 0 条 · 回放 0 fail / 恒 skip 0 · 不变量 0 类 · 登记齐全 · 基线 MATCH**。
任一不满足，先怀疑体检自己坏了（见下一节第 3 条），再怀疑业务代码。

## 三、要特别注意的点（都是踩过坑换来的）

1. **只动 `tests/`**。战斗逻辑、数值（`core/`、`modules/`、`render/`、`content/` …）一律不动；
   体检发现问题只报告、不给业务代码打补丁。确需主代码配合，**先申请**。

2. **禁止用"加豁免 / 折中口径"把红变绿**。规则转 skip 比转 fail 更可疑——那往往意味着它悄悄不再覆盖任何东西。

3. **警惕"工具自身的假绿"，它比红色更危险。** 典型三种：
   - 不打印、不扫描、退出码恒 0（如 `123static-scan` 曾因 Node 自举没进 main 而静默空转，所谓"静态全绿"是空的）；
   - 数据源错位，喂的是**开战快照**而非终局真值 → 真终局值该响的全不响；
   - 扫描层级没下钻（`entries` 子条目）→ 规则"看起来跑过"实则恒 skip。
   判据：**写个探针做负向测试**——人为制造一个已知缺陷，确认工具真的会响。工具没牙 = 报告作废。

4. **逐步不变量优先于终局快照**。中期越界又被自行修回的漂移，终局快照看不到，所以不变量每步都跑。

5. **别把引擎的"设计内中间态"当缺陷**。例：致死统一挂 `_pendingDeath` 交 `resolveDeaths` 结算，
   在结算前那一瞬 `hp<=0 且 alive 仍 true` 是**正常的**。体检判据应与引擎同源
   （`alive && !state._pendingDeath`），红线收窄为「血空了却既没标记待死也没结算」才算断链。
   ——这是"对齐契约"，不是"放宽判据"；反过来也更灵敏（原先误报的 5 条，抹掉标记后照样复报）。

6. **基线是红线中的红线，但不要一律退 1**。`--check` 已二分：**winner 翻转 = 回归**（报红、严禁重录）；
   winner 未变且有明确的业务侧有意变更可解释 = **预期变更**（提示核对后重录）。
   关键在于：重录前必须能说出「这次变化是哪次提交、为什么是有意的」；说不清就别重录。

7. **别复制产品的旧实现**。规则只认可观测契约（渲染后的 type / text / 约定字段），不读引擎内部字段——
   内部字段随时可能被重构搬走（历史上 `clawTargetHpAfter`、顶层 `_baseAtk` 都栽过）。

8. **取证优先于猜测，探针用完即删**。改判据前先跑 `KEYWORDS=` / `DUMP=seed:stage` 之类取证；
   临时探针文件命名 `_tmp-*`，**跑完立即删除**，不许进仓。

## 四、方法沉淀（写规则 / 立不变量之前先对一遍）

> 2026-10-08 并入原 `tests/体检收获与方法.md`（该文件已合并入本文档）。来源：体检线 59 轮迭代 + 6 次复盘。

### 4.1 被反复验证的方法

1. **先取证、再动手**。改判据前先跑 `KEYWORDS=` 文本命中统计 / 一次性探针（顶层 vs 摊平各命中多少），数字可疑就 `DUMP=seed:stage` 打一场全流程。第 4 轮靠这个避免了对着零产出 fact 白改规则；夜间体检第 8 趟靠 dump 澄清了"每回合授予 2~5 条"的假象（摊平后发现每回合其实严格 1 授予 / 1 消耗）。
2. **collectNodes 摊平是第一嫌疑**。历史最高发根因：规则只扫战报顶层 `e.text`，而条目挂在 `attack-group.entries` 子层级（render/30 的 attack-group 自身不带 .text）。129/143/134/144 四条规则全是这么复活的。镜像问题在回放器也存在：第 6 轮修的 `if (e) log.push(e)` 只认单对象，把数组型渲染条目整条吞成黑洞。
3. **渲染后模型是唯一契约**。生产侧渲染时会显式剥离 `factType`/`data`（player/42 L316-324），规则只能靠 `type` + `text` 识别。141 与 142 同题材，141 读被剥离的字段恒 skip 120 场，142 按 type+text 写一直正常——新规则一律照 142 文件头那条行规写。
4. **双向负向测试**。新判据必须构造两份合成战报：一份应 fail、一份应 pass/skip，两份都对才算生效。第 11 轮 `hasTypeProducer` 首版把实产 421 条的 clawHit 误判成"不可达"，就是被"应 pass"那份逮住的——只测"应 fail"会漏假红，只测"应 pass"会漏一刀切不报。
5. **恒 skip 两分法**。skip ≠ 空转：判据是"机制在场 + 条目 0 命中"（例：143 九阳——本场有张无忌且他造成过伤害）。机制没触发是合理 skip，不动；机制在场却 0 命中才是数据源/扫描层级 bug，改数据源。DEAD=1 报出的条目必须逐条做这个区分，不许盲改判据。
6. **零产出三级分类**：不可达 emit 点（自带函数名 + 调用点 file:line + 门控字面量证据）/ 本批次未触发 / 孤儿登记。只报结论不带证据等于把皮球踢回人工（第 4~6 轮的教训）。
7. **不做完整调用图，要"证据可打印"**。JS 静态可达性无解（高阶函数、eventBus 动态派发），硬做必出假阳性；一切判据以"输出里带得出可人工复核的证据"为准，宁可漏判不误判死。也不因"某函数没被 import"就判死——`import()` 与 eventBus 注册都是合法可达路径。
8. **版本头纪律与四方登记**。改动的体检文件自身版本序列 +1、重算 ~bytes、日期 + 一句话；health-rules 规则文件头是"回归规则 / 复发信号 / 对应已修 Bug"三段注释，无版本号。新增规则四方登记缺一不可：121 allRules / 123 SCAN_FILES / 124 RULE_META / tools/106 打包清单。
9. **文本探针要查共用**。`KEYWORDS='反弹'` 与 `'严阵以待'` 同命中 239 条——全部来自 buff 摘要文本，独立 fact 一次都没触发。文本探针的结论必须附一句"该文本是否与其它机制共用"，否则会得出相反结论。
10. **单位会被原地改名，身份别只认显示名**。幼狮成长是同一个 unit 对象改 `cub.name`（`modules/27elite-mingjiao.js:665`，uid / pos 不变），而连击登记按 uid（`core/11:61` → `core/03:371`）。规则消费渲染后条目（只有 type + text，无 uid），必须先把本回合的「X成长为Y（N 号位）」当成别名登记再做比对，否则把狮群的正常回合报成"连击越界"（第 14 轮 146 的两条红全是这个形态）。取名字一律按"不含空白的一段"正则（`([^\s]+?)成长为([^\s（]+)（`）——用 `(.+?)成长为` 会把 🦁 前缀与空格吃进名字，别名键变成「🦁 幼狮」永远对不上（负向测试当场逮到）。
11. **基线重录的前置条件是"已提交 + 有履历条目"**。工作区带着未提交的业务改动跑出 DIFF，一律**只报不重录**：半成品随时会变，且履历里没有可依的有意变更条目，重录等于把中间态固化成红线。等用户提交并补好履历，再对照 winner 是否翻转决定重录。
12. **窗口/状态类判据必须枚举「全部退出分支」，别只认主分支的标记字段**。同一机制常常有多个渲染器变体，标记字段却只写在其中一个上。第 18 轮 139 的误报就是活例：附身窗口有两个关闭点——`renderButterflyReturnFact`（带 `butterflyAction:'return'`）与 `renderButterflyHostDeadFact`（`render/35:363-365`，**不带**该字段，只有 `uidD` + `isDead` + 固定文本）；只认前者 → 宿主一死窗口永不关闭，姐姐此后每一记正常挨打都被判复发。**grep 该族全部渲染器**（`grep -n "butterflyAction\|spiderAction" render/`）比对字段齐不齐，是写这类规则前的必做一步。
13. **阈值/回合一类"会随版本调"的数，判据要从配置读，不要硬编码**。硬编码 6 的 141 在业务把 `tenRoundFortify.round` 由 10 改成 3 后当场假红 20/120 场。判据的正确边界是「配置说几回合就是几回合」，规则只负责校验**实现有没有照配置执行**。口径坑：`getSkillParams(name, key)`（`core/01config-5v5-test.js:24-28`）返回的**就是** params 对象本身（`return skill?.params`），不是 `{name,desc,params}` 外层壳——首版多套一层 `.params` 取不到值 → 全场 `skip=120`，被 `DEAD=1` 当场逮到。**改完规则若某条从 fail 直接变 100% skip，先怀疑取值口径而不是业务。**
14. **合成负向用例要连"规则末尾的 skip 兜底"一起满足**。139 末尾有「`spiderFlyIdx/attachIdx` 均 −1 且 `enemyAttacks===0` → skip」，而 `enemyAttacks` 靠 `beforeE` 里的 uid 判定——探针只喂 log 不喂 `beforeE`，全部"应 pass"用例一律变 skip（第 18 轮首版 6 例假失败全是这个）。**写合成用例前先通读整个函数到 return，把每条 skip 分支的前置条件都垫平。**
15. **版本头 ~bytes 是"写完之后"的值**。填"写头之前"的实测数，新写的头两行本身又占字节 → 写完即失真（第 13 轮两处因此失真 249 / 271，第 14 轮才修）。另：Windows `core.autocrlf=true` 工作区是 CRLF，比仓库 blob 大「行数」个字节，跨口径核对按 `stat` 不按 `git cat-file -s`。
16. **体检文件上的文本改动不要用 Git Bash 的 `sed -i`** —— 它会把 CRLF 全改成 LF（每行掉 1 个 `\r`，121 一次掉 840 字节），`git diff` 会显示整个文件都变了。用 Edit 工具或 node 脚本（`d.replace(/\r\n/g,'\n').replace(/\n/g,'\r\n')` 统一写回）。改完必查 `git diff --stat` 行数是否只有预期那几十行。
17. **回放器全绿、浏览器成片红时，先怀疑「数据源差异」，不要先看数值**。两者的单位快照来源不同：回放器喂真终局，`121` 喂的是 `ctx.UI.allyTeam`（`ui/65main-battle.js:27` 开战 clone，战斗全程不更新）。凡是"终局反推/兜底"型判据（血上限、回满截断、buff 面板字段）在浏览器侧一律失真。**同一份判据在两个 runner 上结论相反，本身就是最强的数据源证据。**
18. **「双喂探针」是证明数据源错位的标准手法**：同一批战报，分别用「真终局」和「疑似错误快照」喂同一条规则，两者 fail 数之差就是误报数。第 19 轮用它一次坐实 143（0 → 40 场）与 144（0 → 25 场），且误报消息里的数字（112.5 / 58 / 182）与用户报数完全吻合 —— **能对上用户原样的误报，才是根因坐实**。

### 4.2 踩坑速查（下次直接照做）

- 回合分隔符「———— 第N回合开始 ————」**不以"第"开头**：`indexOf('第') === 0` 判回合恒得 0，把"每场总数"误读成"每回合条数"；必须用正则 `/第(\d+)回合开始/`。
- Windows 下 `fetch(file://)` 必须走 `fileURLToPath`：`new URL(url).pathname` 会得到 `/C:/...`，拼出双盘符路径直接 ENOENT。
- 技能声明的 `type` 是**配置数据**，在 `content/200game-data.json` 里（`"type": "chainClaw"` 等）。查某 type 的产出方必须连 JSON 一起搜，否则把实产通道误判成死代码。
- 引擎文件顶层访问浏览器全局（window/self）：必须先 mock 再动态 import，全静态 import 直接崩。
- 编号段撞号：`140-baseline.js`（runner 系）与 `health-rules/140-wei-dodge-cloud.js`（规则系）同号。存量不动（改名破坏历史命令可读性），新 runner 文件从 150 起另起段。
- `package.json` 无 `"type": "module"` 会刷 MODULE_TYPELESS 警告并拖慢加载，无害但碍读。
- **回放侧 `_factType` 诊断标签方案已主动放弃**（第 3 轮复盘提出 → 第 10 轮论证后否决，理由写在 `rules-replay.mjs` 注释里）。别再重复提这个方案。

### 4.3 流程与协作收获

- **双 worktree + 只动 tests/** 的边界设计让自动迭代敢放手跑：主代码问题只登记"业务侧待修"不动手，永不污染业务线；也因此从未与业务改动打架。
- **每轮"根因三行"**（根因 / 证据 / 影响范围）写不全不许出方案——定位不清就动手是打转的开始。
- **每轮必 commit、每趟必记一行**（哪怕只写"本轮无改动，各项全绿"）。"跑了没记"和"没跑"无法区分。
- **推送失败不丢账**：日志记"推送失败：原因；本地提交 <sha> 待推"，下轮开场先补推再开新活。
- **复盘员独立复跑对账**：迭代轮声称的数字全部独立复跑核对，并负责修剪日志膨胀、纠正错误归因——"零产出 = 数据源缺失"的错误结论曾连续误导两轮、把 3 条规则错移交业务侧，靠复盘的独立复跑才推翻。
- **预期要与证据对账**：下轮目标的预期数字若与自家 fact 覆盖证据矛盾，先信证据。
- **任务模板里的命令要跟着现实走**：删了文件就要同步改自动化 prompt 里的命令。

### 4.4 体检演进四原则（2026-09-25 定，长期铁律）

1. **口径统一到真值源，且逐步采样**：任何"读单位当前值"的检查一律取 battleStore 真值，不许读 UI 的开战 clone 副本；采样循环中调用＝中期真值，故"中期溢出后被修回"这类漂移也能抓到 —— 终局快照做不到。
2. **不变量优先**：hp∈\[0,maxHp\]、血条==引擎值、pos 唯一、facts 映射完整 —— 每步/每回合断言一次，成本极低、覆盖面最大，且与具体机制无关。新增检查先问：能不能落成不变量。
3. **规则不许复制产品旧实现**：规则只许读「日志」和「可观测输出」（面板 DOM / 战斗实际结果），绝不重读产品的中间状态字段。复制实现＝产品改了规则不改，就一起假绿。
4. **基线要能区分"预期变更"与"回归"**：DIFF 先对提交说明 / 履历条目核对，两类分开报；winner 翻转一律归回归（红线：硬失败、严禁重录），其余归预期变更（提示人工核对后重录）。

### 4.5 不变量类判据的坑（必须先证再立）

- **不变量也会假阳性**（首版两条全错，各作废）：
  - ① 断言 `hp` 为整数 → 引擎内部 hp/maxHp **本就是浮点**（maxHp 可 112.5，百分比治疗天然带小数），取整只发生在显示层 `fmtHp` 与伤害结算 `hpAfter = Math.floor(target.hp) - dmg` → 120 场误报 **11901 条**。
  - ② 用"本次渲染有没有产出"判 facts 映射缺口 → `buffSummary` / `mindControlBanner` **都有注册渲染器**（render/35:498/511），只是在无 buff / 无条件时合法地渲染为空 → 误报 **929 条**。正解是查**注册与否**（render/33 的 `getFactRenderer`），不是查产出。
- **pos 唯一是真不变量**：`render/32:224-226` 渲染按格取第一个单位，`modules/29:232-240` 分配固定位时用 `takenPos` 去重 → 同阵营两个活人占同一格，其中一个将**渲染不出来**。
