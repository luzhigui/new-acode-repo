## 一、什么时候必须走复核

以下任一成立，就**不能**把夜间分支的 tests/ 改动直接 merge/复制进主线：

| 情形 | 为什么危险 |
| --- | --- |
| 判据读取的是 fact 字段或时序（如「往前找最近一条 IMMUNE」） | 两条线的 fact 发射点/顺序可能不同源 |
| 判据依赖主代码尚未落地的转交块 | 夜间用「主代码已修」的假设写判据，main 上必然假红 |
| 判据改了「判定窗口」「归属口径」「取值口径」 | 会改结论，属拍板边界（夜间不替用户拍板） |
| 判据的样本集是夜间自建的定向用例 | 换宿主后用例前提可能不成立 |
| 夜间同时改了主代码（含临时打桩） | 判据与主代码一起搬会把前提一起搬走 |

**不需要走复核**的：纯注释、版本常量、看板/日志、纯文档、只报不判的观察项脚本。

## 二、四步固定跑法

```
# 0) 前置：必须干净树。脏树下回放会拒答（exit 3），结论作废。
git -C <repo> status --porcelain          # 期望：空输出

# 1) 基线（移植前，在 main 工作树上跑，样本集固定）
node tests/rules-replay.mjs > /tmp/base.before.log 2>&1 ; echo "EXIT=$?"

# 2) 移植（只搬 tests/health-rules 下目标规则文件，先不 commit；不要顺手搬主代码）
#    保守做法：先 git stash / 建临时分支，确保可一键回退

# 3) 移植后（同一条命令、同一台机、同 env，不加不减 seed）
node tests/rules-replay.mjs > /tmp/base.after.log 2>&1 ; echo "EXIT=$?"

# 4) 对比（只比这三样：失败规则条数 / 目标规则的 pass·fail·skip / 不变量违规类数）
diff <(grep -E "规则报失败|转交中|恒 skip|不变量违规" /tmp/base.before.log) \
     <(grep -E "规则报失败|转交中|恒 skip|不变量违规" /tmp/base.after.log)
```

**环境一致性三条**（少一条结论就不可比）：

1. 同一台机、同一 node 版本、同一 `tests/health-rules` 之外的依赖（尤其 content/ 与 core/ 未被并行会话改动）；
2. 移植前后 `git diff --stat` 只应出现目标规则文件（多出来的文件就是变量）；
3. 若跑的过程中主代码被改（`git status` 出现 core/modules 变动），ENGFP 变 ⇒ **本组对比作废**，换基线重跑。

## 二·五、整段 diff 先拆块：部分对、部分错，不能整搬也不能整扔

> 第 53 轮实证（看板 #89 / 规则 323）：夜间 V1.3.0 一次改了 73 行，里面混着两块语义完全不同的东西——
> **账本分面**（对：一次击杀同时挂 atk + maxHp 两条，战报次数应只认 atk 面）与
> **乘区归一化**（错：把战报本就正确的 +2 除以乘区算成 1.8，反而制造新红）。
> 整段照搬实测 pass=5/fail=5；只取对的账本分面 pass=6/fail=4（基线 pass=0/fail=10）。

规矩：

1. **按语义块拆**，不按文件大小整搬/整扔。一个 diff 里可能同时有「判据跟随真实机制」和「归因错误的多余计算」。
2. **每块独立走第二节四步**：基线 → 只搬这一块 → 同样本复跑 → 只比三样。块与块之间互不影响时才分别判定。
3. **对的块合入、错的块登记不搬**；错的块写明"为什么错 + 实测数字"，别只写"照搬会红"。
4. 拆块时**不许顺带"简化"**对的块——按原文搬，避免拆的过程中改了口径。

判定表（第三节）照旧适用于每一块，不因为"整段看起来 mostly 对"就放行整段。

## 三、判定表（只认这四格）

| 基线 | 移植后 | 判定 | 动作 |
| --- | --- | --- | --- |
| 红 | 绿 | ✅ 成立 | 合入，看板/日志记「红转绿 + 样本数」 |
| 绿 | 绿 | ✅ 无害 | 合入，记「无变化」 |
| 红 | 红（fail 数不减） | ⚠️ 无收益 | 不合入，登记原因（判据没用 / 样本不触发） |
| **绿 → 红** 或 **fail 变多** | — | ❌ **倒退** | **不合入**，登记 `tests/known-transfers.md`，写明「夜间分支成立、main 不成立」与两行结论 |

★ 第四格是这条规矩的全部意义：**倒退不是「main 的代码旧」，先假设是判据换了宿主就不成立**，
在没逐条读完差异之前，不许写「等主代码落地后自然转绿」这种免责句。

## 四、结论行模板（两行，原样贴进日志与 known-transfers）

```
基线（main 侧，移植前）：N 条失败 / 目标规则 pass=X fail=Y skip=Z / 不变量违规 K 类
移植后（同命令同样本）  ：N' 条失败 / 目标规则 pass=X' fail=Y' skip=Z' / 不变量违规 K' 类 ⇒ 判定：成立 | 无害 | 无收益 | 倒退
```

例（#70 的原始实证，据看板记录）：

```
基线（main 侧，移植前）：— / 断锤 205 pass=5 fail=0
移植后（同命令同样本）  ：— / 断锤 205 pass=4 fail=1 ⇒ 判定：倒退（夜间第253轮修的「IMMUNE 回扫 5 条」不搬）
```

## 五、登记去哪

- **倒退/不移植** → `tests/known-transfers.md` 的「转交中」或新起小节，标题带「跨线移植」字样，
  必须写明两行结论 + 差异所在的 fact 字段/时序；
- **成立并合入** → `tests/体检迭代日志.md` 当轮小节 + 看板对应条目；
- **待拍板（会改结论）** → 看板新开 `open`，正文写清两个选项，不擅自选。

## 六、本单自身的边界

- 不改任何判据：本单只规定「怎么搬」，不规定「搬什么」；
- 不替代 `rules-replay` 的判据：它仍是唯一的 pass/fail 出处，本单只做前后对比；
- 不碰主代码：移植对象限定 `tests/` 下文件；需要主代码配合的一律走转交块。
