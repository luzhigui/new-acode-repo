# 体检「单场覆盖上限」实测 · 全覆盖轮换入口可行方案

> 看板任务：#27「体验层：快速跑完/实时跟跑模式默认不强制任何英雄 → 是否提供『全覆盖轮换』入口待定」
> 验收口径：给出「单场覆盖上限」的说明 + 若做轮换入口的可行方案，拍板前不动大改。
> 本文只给**实测数字**与**方案**，不改任何判据/阈值/基线/主代码。

---

## 一、一句话结论（先看这里）

**「一场 5v5 覆盖不了那些规则」这个前提，实测不成立；而「轮换 N 局能补上」这个指望也基本落空。**

- 干净树实测 12 场单场回放：**每场 177~179 条规则真的跑到了判据并给出结论（规则总数 181 ⇒ 98.3%）**，只 skip 2~4 条。
- **12 场轮换的并集只多覆盖 1 条**（179→180，第 2 场之后曲线不再增长）⇒ **轮换的边际收益 = 0.6%**。
- 轮换后仍不覆盖的那 1 条，要的是「**同场出现特定播报 + 特定 fact**」，**轮换阵容对它无效**。

⇒ 用户在「全能体检」里啥也查不到，**不是因为单场覆盖不了**，而是浏览器入口两件事：
① 120s 超时只跑到第 2 关（`rulePass=0/ruleSkip=0` ⇒ 执行 0 条）；② 工具只认 `issues`、**根本没读** `coverage.verdict`
（看板 #22 已坐实，与本文互为印证）。
⇒ **不建议按「提高覆盖率」建「一键连打 N 局轮换强制阵容」入口**：大改只能换来 0.6%。
该做的顺序是：**先修浏览器入口口径（#22）→ 再给残余规则加定向场次（回放器已有 `DIRECTED_CASES` 机制）**。

## 二、实测口径（怎么量的，可复跑）

- **零改动复用既有回放器**：每跑一场**单场**回放（`SEEDS=x STAGES=y`），从 `RULE_STATS_OUT` 落盘里读每条规则的
  `pass/fail/skip`：`pass+fail>0` ⇒ 这场真的执行了这条规则（没被 skip）；`pass=fail=0` ⇒ 这场它被 skip。
- **不碰主代码、不改判据、不重录基线**：探针 `tests/coverage-ceiling-probe.mjs`（只测量、默认不判红）。
- **必须干净树**：主仓共享工作树常叠 WIP，`#9` 的脏树守卫会直接拦下回放并打「结论作废」——
  本轮第一次在主树跑就是被它拦的（`⚠️ 脏树警告：…恒空转/假绿/覆盖不足结论作废`）。全部数字取自
  干净 detached worktree（`D:/_hc_c27` @`500faa4e`）。
- 复跑命令（单场回放每次要付一次引擎启动 ≈90s，探针支持并行）：
  ```bash
  git worktree add --detach D:/_hc_c27 <commit>
  cd D:/_hc_c27 && node tests/coverage-ceiling-probe.mjs --cases 12 --jobs 4 --json <out.json>
  ```

## 三、单场覆盖上限（实测 + 静态上界）

### 3.1 实测（每场单场回放，规则总数 181；12 场跨 seed1×7 关 + seed2×5 关）

| 场次 | 执行/总数 | skip |
|------|-----------|------|
| seed=1 stage=1 | 178/181 | 3 |
| seed=1 stage=2 | 178/181 | 3 |
| seed=1 stage=3 | 179/181 | 2 |
| seed=1 stage=4 | 178/181 | 3 |
| seed=1 stage=5 | 178/181 | 3 |
| seed=1 stage=6 | 177/181 | 4 |
| seed=1 stage=7 | 178/181 | 3 |
| seed=2 stage=1 | 177/181 | 4 |
| seed=2 stage=2 | 178/181 | 3 |
| seed=2 stage=3 | 177/181 | 4 |
| seed=2 stage=4 | 179/181 | 2 |
| seed=2 stage=5 | 179/181 | 2 |

**单场执行条数：max 179 / 中位 178 / min 177 / 均值 178.0（规则总数 181）⇒ 98.3%**

### 3.2 静态上界（为什么"5v5 覆盖不了"这个推理不成立）

`tests/124rule-recipes.js` 的 `RULE_META` 登记 **170 条**规则名 → 英雄标签映射：
**只有 33 条规则绑了英雄标签**（我方 19 条 + 敌方 14 条，按最优阵容算），其余 ~148 条与具体英雄无关
（`generic:` / `mechanic:` / 未登记）——它们盯的是数值同源、注册一致性、账实一致这类**与阵容无关**的判据。

标签分布（前 12）：

| 标签 | 规则数 |
|------|--------|
| hero:小昭 | 9 |
| enemy:宋青书 | 4 |
| enemy:唐文亮 | 4 |
| hero:张无忌 | 3 |
| hero:韦一笑 | 3 |
| hero:谢逊 | 3 |
| enemy:何太冲 | 3 |
| enemy:张三丰 | 2 |
| enemy:周芷若 | 1 |
| enemy:玄冥二老 | 1 |
| hero:张三丰 | 1 |
| enemy:空见 | 1 |

- 最优阵容下**我方 5 人**（张无忌、韦一笑、小昭、张三丰、谢逊）可查 **19 条**；
- **敌方 5 人**（宋青书、周芷若、唐文亮、张三丰、何太冲）可查 **14 条**；
- ⇒ 静态上界 ≈ **33 条带标签规则** + 148 条无英雄要求。

**关键对照**：只有 33 条规则是"英雄必须在场才查"的，而实测单场跑到了 178 条
⇒ 说明**绝大多数规则不是靠"英雄在场"才成立**，而是靠战报里有没有对应事实（fact）来决定跑不跑。
所以"一场只有 5 人、规则涉及 20+ 英雄 ⇒ 覆盖不了"这条推理链**在数据上断了**。

## 四、轮换能补多少

- **12 场轮换的并集覆盖 = 180/181 条（99.4%）**。
- **贪心累计曲线：1 场→179，2 场→180，3~12 场→180（不再增长）**
  ⇒ **轮换的边际收益 = 1 条规则（0.6%）**，而且第 2 场之后就吃满了。
- 12 场轮换后**仍未执行**的只有 **1 条**：
  `惑心换位排除袋中单位(回归)`［tag: `mechanic:惑人心智`］
  —— 311 的前提是「**同场**有『说不得装袋』播报 + 惑心换位 fact，缺一不可」
  ⇒ 它要的是**特定事件组合**，不是"英雄在场"，**轮换阵容对它无效**。

## 五、结论与可行方案（拍板前不动大改）

### 5.1 结论

1. **单场覆盖上限 ≈ 178/181 条（98.3%）** ——「一场 5v5 覆盖不了」的推理在数据上断了。
2. **轮换 12 场只多覆盖 1 条**（179→180），且第 2 场之后再无增长 ⇒ **轮换的边际收益 = 0.6%**。
3. 残余那 1 条要的是"特定事件同场出现"，**轮换阵容解决不了**，只能靠**定向构造场次**（回放器已有 `DIRECTED_CASES` 机制）。
4. ⇒ **不建议建「一键连打 N 局轮换强制阵容」入口**：大改换 0.6% 覆盖率。
   用户看不到真红的真因在浏览器入口（120s 超时只跑到第 2 关 ⇒ 执行 0 条；工具只认 `issues` 没读 `coverage.verdict`），
   看板 #22 已坐实——**那两条修完的收益远大于轮换入口**。

### 5.2 轮换入口若还要做，只剩两条理由 —— 实测把两条都削薄了

- **理由一：补掉残余规则** —— 12 场轮换后仍剩 **1 条**，而它要的是"同场特定播报 + 特定 fact"，
  **轮换阵容对它无效**。⇒ 这条理由指向的是「给某条规则加一个定向场次」，不是「给用户一个轮换按钮」。
- **理由二：多局样本降低偶发红/绿概率** —— 本轮 12 场实测里**每场的失败规则数稳定在 22~23 条**
  （差异只来自那 1 条规则），看不出"多打几局会改变结论"的迹象。
  真要评估该收益，**先在 node 侧用既有 20 seed × 7 关样本量一量**，别先做入口。

### 5.3 分级方案（改动量从小到大）

| 方案 | 改哪 | 做什么 | 量级 | 谁做 |
|------|------|--------|------|------|
| 方案 0（**建议先做**） | 只改报告 | 把「单场覆盖 178/181（98.3%）、未覆盖 N 条及其原因」写进一键报告与人话翻译（`tests/one-click-health.mjs` + `tools/806`），让用户先**看见覆盖口径** | 小 | 体检侧 |
| 方案 A（node 侧，可自做） | `tests/rules-replay.mjs` 的 `DIRECTED_CASES` | 把残余规则（当前 1 条：311 惑心换位排除袋中单位）补成**定向场次**——回放器已有这套机制，改动局限在 tests/ | 小 | 体检侧 |
| 方案 B（体验层，**收益有限**） | `tests/121health-monitor.js` | 加 `?rounds=N&rotate=1`：每关轮换一组强制标签并累计覆盖（121 已有 `rulePassNames` 累计底座 + `coverage.verdict` 输出，缺的是"换阵容"）。**按本轮实测，收益 ≈ 1 条规则** | 中大 | 体检侧 |
| 方案 C（产品层） | 一键入口 | 加「轮次」参数 + 覆盖报告 | 大 | **拍板后再动** |

### 5.4 硬约束（做方案 B 前必须知道，否则一定做歪）

- **force 开关只在开局生效**：主代码 `modules/330-battle-init.js:181-194` 在 `initBattleTeams` 里读
  `forceZhang/forceWei/forceXieXun/forceHanLiSa/forceXiaoZhao` ⇒ **换阵容必须重开一局**，局内改无效。
- **明教侧锁位恒为 3**：`modules/330:398-402`「四人同时在队时张/韦保锁、小昭/谢逊按序让位，锁位总数恒为 3」
  ⇒ 轮换能换的"我方组合"数量有限（张/韦/小昭/谢逊 里锁 3 + 寒离飒插队首位），不是 5! 种自由组合。
- **敌方靠随机精英 + 变体**：敌方标签规则（宋青书/唐文亮/何太冲…）多数只能靠随机出阵碰到；
  `forcePang` 是唯一能指定敌方阵容变体的开关（`modules/330:417-423`，且第三关才有含胖远桥的变体）。
- **转交中与恒 skip 的规则不因轮换改善**：`known-transfers.md` 里的转交项属主代码待落地；
  恒 skip（空转）属规则自身问题（另一条主线：分支级空转自检）。
- **口径提醒**：规则"执行了"≠"查到位了"。本轮口径是 `pass+fail>0`（跑到了判据并给结论）；
  规则自身"没素材也 return pass"属于分支级空转（另一条主线），别把 98.3% 说成"98.3% 的问题都查过了"。

### 5.5 报告口径提醒（别再把"没查到"说成"没问题"）

无论做不做轮换入口，报告口径都应写成：
「本场覆盖 178/181 条规则（98.3%），**未覆盖的 1 条**（原因：需特定事件同场）——不代表这 1 条没问题」。
这正是 `#22` 要修的那件事，与轮换入口**解耦**：先修口径，再谈要不要多打几局。
