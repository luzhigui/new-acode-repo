// ==================== 一、核心铁律 (11条) ====================

1. 发代码必须经总座确认
   - 任何代码修改，发送前必须等总座确认，禁止擅自改动。
   - 优先发前后对比（旧代码块必须准确 → 新代码块），不要动不动发整个文件。
   - 每次最多发 3 处改动，发完等用户确认后再继续下一批。
   - 旧代码来源铁律：必须从用户提供的真实文件中逐字提取，禁止凭记忆重写。
     如果用户搜不到 AI 给的旧代码 → 用户直接贴函数原文 → AI 基于原文做替换。
     这是经过多次实战验证的唯一可靠方式。
   - AI 发出前后对比后，默认总座会直接应用改动，无需额外询问"要开始改吗？"。
   - 问题还在讨论阶段时（总座没明确说"改"），禁止主动说"现在改吗？"然后直接发代码块。先讨论清楚，等总座明确指令再动手。
   - 分析根因后，即使自认为"已经讨论清楚了"，也必须等总座说出"改吧""发吧""开始"等明确指令后才能发代码。禁止分析完直接趁热打铁发代码。

2. 错误可见，不靠瞎猜
   - 异常必须在页面底部红色面板显示（24error-capture.js），手机端也能看。

3. 找全链条根因，不兜底
   - Bug 修复必须先找到问题发生的全链条真正原因，从源头解决。
   - 实在找不到根因，经用户确认后才可以实施兜底方案。
   - 禁止没找到原因就直接绕过去、掩盖问题、或用"看起来修好了"的方式交差。
   - 典型案例：普通模式全海克斯 → 误判为筛选逻辑错误，跳过诊断直接改业务代码，导致问题加剧。正解：先确认环境状态（localStorage残留），定位到入口分发，一行修复。

4. 定位优先，修复滞后
   - 先找到根因再动手。同一问题连续两次修不好，立刻停手回最小单元排查。

5. 禁止凭感觉改代码
   - 凡涉战斗规则、数值、Buff，不确定就问，严禁"猜测式修改"。
   - 数值改动前优先用控制台脚本跑分布验证（如防战 K 值枚举），确认合理后再动代码。

6. 函数职责单一，看动分离
   - 纯计算、纯判定、纯渲染必须隔离。播放器只消费日志，不参与计算。
   -（备注：当前 `processUnitAttack` 已膨胀至处理多种机制，后续重构时优先拆分。）

7. 数据驱动视图
   - 特效走数据标记（_flash、_blocked、_flyMode 等），renderGrid 统一读取渲染。
   - 禁止特效函数直接操作 DOM。
   - 每次加特效调用前，先做分层检查：这行代码放在引擎层还是播放器层？引擎只产出日志数据，播放器消费日志驱动 UI。特效函数（showDamageFloat/showHealFloat/showAtkBuffFloat 等）一律只能出现在播放器层，严禁写入 core/ 目录下的任何文件。
   -（成功案例：成昆幻影伪装全程通过 `_phantomTarget` 字段流转，零越界。）

8. 实验室代码逐行复刻
   - 验证通过的函数原样搬入，不做"等价改写"。特效参数提到文件顶部可调。

9. 交付前自审完整性
   - 所有导出函数有实际实现、文件末尾完整、无注释占位符。
   - 禁止"和之前一样"之类的省略。

10. 精英技能完全配置化
    - 参数全在 core/01config-5v5-test.js 的 ELITE_SKILLS。
    - 通用精英逻辑在 modules/23elite-skills.js；阵营化精英组件在 modules/97elite-imperial.js、modules/98elite-sixsects.js、modules/99elite-mingjiao.js。
    - UI 只读取配置，不硬编码。

11. 新增单位属性必须贯通四步链路
    - 新增任何单位字段（如 _phantomTarget）必须依次修改：引擎 emit → 事件流 → Store 同步 → UI 读取，四步缺一不可。漏任何一步都会导致"改了但没生效"。


// ==================== 二、代码交付标准 (4条) ====================

1. 前后对比优先
   格式："旧代码块：" + 旧代码 + "新代码块：" + 新代码。
   仅大改动或跨文件才发完整文件。

2. 文件头部规范
   // 文件名 - 描述
   // 预估行数/字符, 时间, 版本
   export const VER = '文件名 Vx.x.x';

3. 版本号统一
   格式 VX.X.X，发版前全文件对齐。当前统一 V5.3.1。

4. 大文件分片规范
   超 40000 字符自动分片，头部注明 [第 N/M 片]，结尾附确认提示。


// ==================== 三、经验案例库 (9条) ====================

1. 死机排查：先看红色错误面板，再 F12，逐函数追溯，不凭感觉。
2. 数据污染：找源头改，不靠清理循环打补丁。先问"还有哪些地方能改这个数据？"
3. 特效时序：横幅预告在特效前；暂停期间 isPaused=true 确保 DOM 查询准确。
4. 特效残留：飞撞后必须恢复 opacity/visibility/display/filter/transform 全部样式。
5. 模块合并：变量名唯一化、import 用 [\s\S]*? 跨行匹配、用绝对路径。
6. 架构升级 · 数据流原则：
   - 引擎通过 EventBus 发射信号（beforeAttack/afterAttack 等），UI 消费事件，日志同步生成。
   - 状态与动画彻底分离：动画只触发视觉，不修改 hp/alive 等状态。
   - 统计字段（dmgDealt/dmgTaken/healDone 等）通过事件绝对值传递，UI 侧直接赋值，避免重复累加。

7. 诊断优先于修复：
   - 先确定"能不能看到"（劫持 appendChild / MutationObserver / 函数调用），再确定"位置对不对"（打红点 / 打印 getBoundingClientRect），最后才动手修。
   - 控制台注入诊断脚本，不修改代码文件，刷新即恢复。严禁在源代码里加 debugDot 等临时调试元素。
   - 成功案例：反击风暴排查 → 劫持 appendChild 确认元素已插入、MutationObserver 确认动画运行、红点确认位置正确，最终定位到内联 transform 覆盖 CSS 动画。

8. 旧代码精确定位是最高优先级：
   - 如果用户两次说"搜不到"，立即切换方式：让用户贴目标函数完整原文 → 基于原文逐字提取旧代码块。
   - 禁止凭上一轮的修改记忆推测当前文件内容，文件可能已被用户手动改动。
   - 成功案例：全自动 btnMain 改动 → 第一次旧代码搜不到，用户贴全文后精准匹配到 `doStartBattle` 段，一举替换成功。

9. 全局规则改动必须穷举影响面：
   - 改动通用函数（如 shouldStartNewGroup）后，列出所有调用场景逐一验证，避免遗漏边界 case。
   - 多个入口（btnMain / btnSettle / switchToStage）要做相同改动时，逐处对齐，避免漏改导致状态不一致。

10. 日志分层播放：先分类，再定速
   - 战斗日志按信息重要性分层：一档（战斗文本、伤害行）不可压缩，锁常速；二档（波动、计算）半跟随倍速；三档（破防、坚盾等提示）整行弹出不逐字。
   - 加速时重要信息不丢，减速时次要信息不拖沓。切勿一刀切地用同一个速度变量控制所有日志。
