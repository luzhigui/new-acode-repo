### 一、10条经验教训（完整详细版）

**1. 数据污染排查六步**

**来源**：1v1模式合成死格残留问题

**问题描述**

合成消耗了3件道具，位置8上却还有一个同名死格。反复修改 `autoSynthesize` 函数至少6个版本，改清理逻辑、改删除顺序、改循环条件，每次都是无效修改。

**错误做法**

死盯着核心逻辑函数，在被污染的数据上反复修补，不断加清理循环、改执行顺序，但问题始终存在。

**排查过程**

最终发现是 `index.html` 里 `btnInvest` 的回调在 `doInvest` 执行完毕后，又额外调用了一次 `setDrop`，把已经被消耗的道具重新放回了场上。污染源不在核心函数内部，而在外部调用方。

**正确做法**

数据被污染了，先排查所有可能修改数据的入口，找到污染物源头，再修复。排查口诀：先问自己"还有哪些地方能改这个数据？"，把所有入口列出来逐一排除。入口可能不止一个。

**核心教训**

不要在坏数据上反复修补。出现"数据多了/错了"，先找到源头，而不是忙着清理或修正。

---

**2. 函数职责单一**

**来源**：1v1模式合成系统重构

**问题描述**

`autoSynthesize` 函数同时负责：统计场上道具、判断能否合成、删除格子、拾取道具、输出日志、设置特效。六件事混在一起，任何一步出问题都难以定位，而且修改统计逻辑时可能意外影响拾取逻辑。

**错误做法**

认为"一个函数能完成的事就不分两个"，把所有逻辑堆在一起。

**正确做法**

拆分为 `checkSynth`（只读检测）和 `executeSynth`（只写执行）。检测函数不修改任何状态，执行函数只管消耗和拾取。核心判断标准：如果一个函数同时做了"看"和"动"两件事，立刻拆分。检测和执行的分离是最基本的职责边界。

**核心教训**

看和动必须分开。函数职责单一，不是减少代码量，而是减少排查难度。

---

**3. 状态隔离**

**来源**：1v1模式合成类型锁混乱

**问题描述**

`synthCount` 和 `typeDead` 是全局共享的。敌方合成蓝装后，我方的同类型道具也变成了死格；敌方的合成次数被算到我方锤子上。结果是我方莫名其妙获得了锤子，或者我方道具莫名其妙被锁。

**错误做法**

认为"敌我双方只是两个单位，共用一个全局计数器很自然"，设计阶段没考虑阵营隔离。

**正确做法**

`allySynthCount` 和 `enemySynthCount` 独立计数，`allyTypeDead` 和 `enemyTypeDead` 独立锁类型。双方的任何状态都不互相影响。设计阶段就问清楚：这个状态是全局的还是独立阵营的？如果有"双方"这个概念，状态大概率需要隔离。

**核心教训**

独立阵营的状态必须独立存储。不要用共享变量偷懒，早晚出问题。

---

**4. 顺序就是逻辑**

**来源**：1v1模式投资与合成调用顺序

**问题描述**

`doInvest` 里先调用 `autoSynthesize` 检测合成，再用 `setDrop` 放道具。结果第三件白装掉落后，要等下一次投资才能被检测到，而此时它已经因为类型锁死变成了死格。

**错误做法**

认为"函数内部逻辑正确就行，调用顺序不重要"，先检测再放数据。

**正确做法**

先放道具，再检测合成。新道具落地后立即参与合成判定。在做任何检测之前，先确认数据是否已经就绪。顺序就是逻辑，顺序错了，逻辑不存在。

**核心教训**

数据没就绪就不要做检测。先准备好数据，再做判断。

**5. 治标不如治本**

**来源**：1v1模式道具残留问题

**问题描述**

合成后偶尔有多余道具残留，于是加了一个遍历所有格子强制清理同类型白装的循环。结果是残留没清掉，反而把没参与合成的正常道具也一并删了，造成了更大的混乱。

**错误做法**

在不知道残留原因的情况下，直接写清理逻辑来删掉"多余"的东西。

**正确做法**

先找到残留道具是怎么产生的——还是那个多余的 `setDrop` 调用。修复源头后，残留自动消失，不需要任何额外清理。出现"数据多了"，先问"是谁写进来的"，而不是"怎么删掉"。删东西是最危险的修复方式，很容易误删正常数据。

**核心教训**

打补丁之前先找源头。盲目的清理循环比残留本身更危险。

**6. 全局视野排查**

**来源**：1v1模式合成问题持续排查

**问题描述**

连续十几个版本都在改 `1v1-core.js`，函数重写了多次，逻辑调了又调，但问题始终存在。因为问题根本不在 `core.js`，而在 `index.html` 那行多余的 `setDrop`。只盯着一个文件看，从来没想过去检查调用方。

**错误做法**

反复检查核心逻辑文件，逻辑确认无误但问题还在，就继续在同一个文件里找。

**正确做法**

当一个文件已经反复检查多次、逻辑确认无误但问题依然存在时，立刻转向检查其他文件。数据在整个系统中流动，污染可能发生在任何节点。调用方、事件绑定、回调函数——这些都是容易忽略的污染源。

**核心教训**

问题可能不在你正在看的那个文件里。视野要从核心逻辑扩展到所有交互点。

**7. 模块合并三要素**

**来源**：多个JS文件合并成单HTML文件

**问题一：变量名全局冲突**

每个模块都有 `export const VER = '...'`，简单删掉 `export` 后变成五个同名的 `const VER`，合并后全局作用域下直接冲突，报错 `Identifier 'VER' has already been declared`。同类冲突还有 `const C = CONFIG`、`const S = STATE`、`const KT = KILL_TAUNT`。

**修复**：给每个模块的变量分配唯一名称（`VER_CONFIG`、`VER_CORE`、`VER_BATTLE`等）。

**问题二：模块语法残留**

简单正则 `import\s+.*?from\s+['"].*?['"];?` 无法匹配跨行 import。浏览器看到残留的 `import` 关键字直接报错 `Cannot use import statement outside a module`。

**修复**：换用 `import\s+[\s\S]*?from\s+['"].*?['"];?`，`[\s\S]` 匹配包括换行在内的任意字符。同时确认 `export async function`、`export default`、`export { ... }` 三种变体全部移除。

**问题三：路径依赖**

相对路径依赖当前工作目录，不同位置执行结果不同，报 `MODULE_NOT_FOUND`。

**修复**：使用 `path.join(__dirname, filename)` 构建绝对路径，无论从哪里执行都能正确定位。

**核心教训**

模块合并不是简单拼接。必须逐文件列出所有顶层变量确保不重名、正则必须覆盖跨行、路径必须用绝对路径。

**8. 模块化重构六条**

**来源**：彪，V2.0重构期间总结

**第一条：模块化不等于互相引用**
模块拆分的目的是"分而治之"，不是让每个模块都引用其他模块，那样不是解耦是织网。正确的做法是所有模块只和调度中心（main）单向交互，模块之间不互相 import。

**第二条：接口能少就少，参数能简单就简单**
每次给模块加一个导入导出，就多一个断裂点。十几个模块、几十个接口，全靠人肉核对，早晚出错。接口越少越稳。

**第三条：不要为了用不上的灵活性牺牲稳定性**
接口设计要"刚好够用"，不要为了将来可能用到的扩展而预留过多的抽象层。先稳定，再扩展。

**第四条：项目规模决定架构复杂度**
小项目不需要企业级的依赖注入和模块抽象。简单、直接、跑得通，比优雅、复杂、容易崩重要得多。

**第五条：改代码之前先核对接口**
每次修改一个模块的导出名，必须检查所有引用它的模块是否同步更新。一份接口对照表比十次调试有用。

**第六条：测试环境不等于用户环境**
手机端、ACode、不同浏览器的模块加载机制有差异，本地能跑不代表用户端能跑。尽可能贴近用户环境验证。

**9. 交付前自审函数完整性**

**来源**：胜利特效不显示问题

**问题描述**

胜利特效不显示，排查了半天改了很多地方。最终发现是 `ui-render.js` 里的 `spawnVictoryEffects` 函数体是注释占位符 `/* ... 原逻辑 ... */`，不是实际代码。注释看起来像代码，但执行时什么都不做。

**错误做法**

发代码前只确认"文件结构完整"，没有逐函数检查是否有实际实现。用注释代替函数体方便了自己，坑了接收方。

**正确做法**

发送文件前必须逐项检查：
1. 所有导出函数是否有实际实现（不是注释占位）
2. 文件末尾是否完整
3. 有无残留的注释占位符（`/* ... 原逻辑 ... */` 等）

禁止用注释代替函数体。交付代码时，任何函数体都不能是注释，必须是完整可执行的代码。

**核心教训**

注释不是代码。"完整文件"不只是文件结构完整，还包括每个函数都是可执行的。

**10. 排查从末端向上追溯**

**来源**：胜利特效不显示问题排查

**问题描述**

胜利特效不显示，一直在改 `main`、改 `player-core`、改 `buff-ui`，始终没定位。排查方向是从中间层往两边看，改来改去都没有触及真正的问题。后来发现是 `ui-render` 里的 `spawnVictoryEffects` 函数体不完整——这个函数是胜利特效的最终调用处，但排查时从来没想过去检查它。

**错误做法**

排查从中间层开始，沿着调用链往下改，没有先确认最终调用处的函数是否完整。

**正确做法**

排查从最终调用处（渲染层）开始，先确认最底层函数是否完整，再沿调用链向上追溯。几分钟能定位的问题，不要在错误方向反复撞。如果底层函数完整但结果不对，再逐层往上查调用方。

**核心教训**

从末端开始查，不要从中间开始。最底层的函数是问题最容易藏的地方，也是排查最应该先看的地方。

**11. 音频系统故障隔离**

**来源**：BGM 加载失败导致音效全局关闭

**问题描述**

BGM 文件加载失败时，整个音频系统（包括音效 SFX）全部失效。玩家听不到任何声音。

**根因分析**

`AudioManager.init()` 中 BGM 加载失败后把 `this.enabled = false`，而 `playSfx()` 开头检查 `if (!this.enabled) return`，导致 BGM 失败连带禁用了所有音效。两个本应独立的音频子系统被一个标志位耦合在一起。

**正确做法**

BGM 和 SFX 是独立的音频通道，一个失败不应影响另一个。修复：BGM 加载失败只设 `bgmBuffer = null` 和 `_bgmFailed = true`，`playSfx()` 不受 `_bgmFailed` 影响。完整代码见 `modules/28audio-manager.js`。

**核心教训**

不同子系统的故障必须隔离。一个模块加载失败时，只标记该模块不可用，不要通过共享标志位（如 `enabled`）连带禁用其他独立模块。

**12. 事件信号必须覆盖所有代码路径**

**来源**：未命中时 afterMiss 信号未发射

**问题描述**

V5.3.0 事件总线重构后，概率连击、宋青书性奋、小昭永久连击等精英技能在攻击未命中时完全不触发。

**根因分析**

`resolveAttackHit` 中未命中分支只 push 了日志和设 `_acted = true`，没有发射 `afterMiss` 信号。监听该信号的精英技能处理器从未被调用。命中路径的 `afterAttack` 信号正常，所以问题只出现在未命中时。

**正确做法**

在未命中分支添加 `eventBus.emit('afterMiss', data)`，让监听器有机会设置重试。修复后三条精英技能链路（概率连击 priority 40、宋青书性奋 priority 50、小昭永久连击 priority 60）均正常触发。完整代码见 `core/49battle-attack-steps.js`。

**核心教训**

事件驱动架构中，每个分支路径（命中/未命中/闪避/死亡）都必须发射对应的信号。重构后要逐路径验证信号是否完整，不能只测正常路径。

**13. 重试逻辑必须重置状态标志**

**来源**：宋青书不攻击第二次（P0）

**问题描述**

`afterMiss` 信号修复后，宋青书的性奋重试仍不生效——信号触发了、日志也打印了"获得额外攻击机会"，但宋青书没有实际执行第二次攻击。

**根因分析**

`resolveAttackHit` 未命中时设了 `unit._acted = true`。性奋监听器设 `data.retry = true` 后，`processUnitAttack` 递归调用自身执行重试，但 `_acted` 仍为 `true`。对比概率连击（priority 40）和小昭永久连击（priority 60）的处理器——它们都显式写了 `unit._acted = false`，而宋青书性奋处理器（priority 50）漏了这一行。

**正确做法**

重试前必须重置 `unit._acted = false`，与其他两个重试处理器保持一致。完整代码见 `core/48battle-round.js`。

**核心教训**

重试/递归调用前，检查所有可能阻止执行的状态标志（`_acted`、`_doubleStriked` 等）。同类处理器之间要对比状态重置逻辑，确保模式一致。

### 三、技术标准类四项

**1. 攻击/被攻击/死亡颜色样式**

**驱动方式**：通过 `Unit` 对象上的 `_flash` 属性标记状态，`renderGrid` 渲染时读取并设置 `data-flash` 属性，CSS 属性选择器自动匹配生效。

**使用方式**：`unit._flash = 'attack' | 'defend' | 'dead' | null`，渲染层读取 `data-flash` 属性匹配 CSS。

**三种状态**：攻击高亮（蓝色 `#1e6bb8`，z-index 999，scale 1.1）、被攻击高亮（金色 `#f1c40f`，z-index 998，scale 1.05）、死亡状态（红色 `#e74c3c`，z-index 1001，scale 0.9，居中 `✕` 标记）。z-index 规则：攻击 > 防御，确保双方同时高亮时攻击者在上层。

**渲染层逻辑**：`renderGrid` 检测 `unit._flash === 'dead' || !unit.alive` 时创建 `dead-mark` span，显示 `✕` 字符。完整 CSS 和渲染代码见 `ui/14ui-render-5v5-test.js`。

**设计原则**：数据与表现分离。特效状态存储在数据层（`unit._flash`），渲染层只读标记来决定视觉。不在特效函数中直接操作DOM改颜色，因为 `renderGrid` 随时可能重绘，手动样式会被覆盖。

**4. 火焰绑定方式**

**来源**：闪避反击最终流畅版的技术方案

**核心思路**：尾焰不再作为独立的绝对定位元素自己飞，而是直接挂载在攻击者克隆体内部作为子元素，利用 CSS 定位自动跟随父元素移动。

**旧方案的问题（独立元素方式）**：
- 火焰和攻击者是两个独立元素，必须在每帧动画循环里手动同步位置
- 漏一帧就出现火焰"抢跑"或"落后"
- 偏移量（60px/110px）调了很多次都对不齐
- 清理时需要分别删除两个元素

**绑定方式（新方案）**：

创建 `flame-trail` 容器直接挂载到攻击者克隆体内部，内含多层 `flame-layer`（6色渐变：`#ff4500`→`#ffff00`，尺寸递减，`flameFlicker` 动画）。CSS 用 `position: absolute` 定位，删父元素时子元素自动清除。完整实现见 `fx/17fx-crash-5v5-test.js`。

**两种方式对比**：

| 维度 | 独立元素方式 | 绑定方式 |
|------|------------|---------|
| DOM 关系 | 火焰和攻击者是兄弟元素 | 火焰是攻击者的子元素 |
| 位置同步 | 每帧手动更新火焰坐标 | CSS 自动跟随父元素 |
| 偏移风险 | 偏移量需反复调试 | CSS 一次写死即可 |
| 清理 | 需要分别删除两个元素 | 删父元素时子元素自动清除 |
| 代码量 | 每帧多两行同步代码 | 创建后无需维护 |

**适用范围**：所有附着在角色身上的视觉元素——尾焰、光晕、气流分流、风盾、呼吸光晕等。

**推荐做法**：凡是需要跟随角色移动的特效元素，优先挂为子元素，利用 DOM 层级自动跟随。只有当元素需要脱离角色独立运动时（如溅射箭从防御者飞向相邻敌人），才使用独立定位。

### 四、技术决策档案

**1. 引擎-UI解耦修复规划**

**来源**：总策划
**日期**：2026-07-11
**定位**：V5架构重构的核心技术决策，定义引擎与UI的明确边界

**核心问题**

引擎越界了。战斗引擎在计算完一轮攻击后，通过 `window._emitEvent` 和 `window._battleEvents` 全局变量直接操作 UI Store，导致播放器还没播动画，画面已经变了。

具体表现：
- 换位效果：引擎算完直接改了 `unit.pos`，播放器播换位动画时数据已经变了
- 伤害扣血：引擎算完直接改了 `unit.hp`，伤害飘字动画还没播血条已经掉了
- 死亡处理：引擎直接设了 `unit.alive = false`，死亡特效还没播格子已经红了

这违反了"数据与表现分离"的核心准则——引擎是算账的，不应该管画面什么时候更新。

**修复三步走**

**第一步：切断引擎的所有 UI 通道**

删除引擎中所有直接操作 Store 的代码：

| 删除项 | 所在文件 | 说明 |
|--------|---------|------|
| `window._emitEvent` 调用 | `core/04buff-system.js` | Buff触发换位/击退时不再发射事件 |
| `window._battleEvents` 写入 | `core/06battle-engine-core.js` | 引擎不再向全局事件队列推送数据 |
| 直接修改 `unit.pos` | `modules/23elite-skills.js` | 精英技能触发的位置变化只写日志 |

替代方案：引擎只把旧位置、新位置写入战斗日志（`log` 数组），不碰 Store。

**第二步：播放器自己掌控 Store**

播放器读取战斗日志，自己决定何时更新 Store：

| 场景 | 更新时机 |
|------|---------|
| 换位 | 换位动画播放完毕后，才修改 `unit.pos` |
| 伤害 | 伤害数字飘完、血条动画播完后，才修改 `unit.hp` |
| 死亡 | 死亡红光缩小+✕特效播完后，才设 `_isDead = true` |
| Buff效果 | `APPLY_EVENTS` 只在攻击日志播放完毕后执行 |

**第三步：补全死亡结算**

| 修复项 | 说明 |
|--------|------|
| 统一设置 `_isDead = true` | 所有致死路径都必须设置此标记 |
| 死亡后清除 Buff | 单位死亡后立即从 `activeBuffs` 中移除其相关效果 |
| 溅射不读死人属性 | 流星赶月溅射伤害计算时，跳过已死亡单位 |

**涉及文件清单**

| 文件 | 改动内容 |
|------|---------|
| `core/04buff-system.js` | 删除 `window._emitEvent`；换位/击退只写日志 |
| `core/06battle-engine-core.js` | 删除 `window._battleEvents`；死亡路径统一设 `_isDead` |
| `modules/23elite-skills.js` | 删除位置直接修改；改走日志 |
| `player/10player-core.js` | 读取日志控制 Store 更新时机；`APPLY_EVENTS` 延后执行 |

**目标状态**

```
改完后：
  引擎 → 只算账、写流水账
  播放器 → 读流水账、播动画、更新画面
  各司其职，互不越界
```

**2. 按钮控制逻辑**

**文件**：`ui/44ui-controls.js` V5.0.1
**职责**：倍速系统 + 按钮状态管理
**日期**：2026-07-07

**倍速系统：双轨并行设计**

**核心设计理念**：手动锁定倍速和滚动自动慢放两套逻辑互不干扰，用户可以手动锁定一个倍速，滚动日志时自动切换到0.5x慢放，滚回底部后自动恢复到之前锁定的倍速。

**关键变量**：

| 变量 | 类型 | 作用 |
|------|------|------|
| `manualSpeedLock` | boolean | 用户是否手动锁定了某个倍速 |
| `manualSpeedValue` | number | 锁定的倍速值（500/143/250/1800） |
| `slideSpeedActive` | boolean | 当前是否正常播放。`false` = 正在滚动慢放中 |
| `preManualSpeedLock` | boolean | 进入慢放前保存的手动锁状态 |
| `preManualSpeedValue` | number | 进入慢放前保存的手动锁数值 |

**三个核心场景的行为逻辑**

**场景一：用户点击倍速按钮**

```
点击已高亮的按钮：
  → 取消手动锁定（manualSpeedLock = false）
  → 恢复常速 500ms
  → 所有按钮不高亮

点击未高亮的按钮：
  → 锁定该倍速（manualSpeedLock = true, manualSpeedValue = 新值）
  → 该按钮高亮
```

**场景二：用户上滑日志（触发慢放）**

```
activateScrollSlowdown() 执行：
  → 保存当前手动锁状态到 preManualSpeedLock / preManualSpeedValue
  → 设置 slideSpeedActive = false（标记进入慢放状态）
  → 速度切换到 1800ms（0.5x）
  → 0.5x 按钮高亮
  → 如果之前手动锁定了非0.5x倍速，该按钮半高亮
```

**场景三：用户滚回底部（退出慢放）**

```
restoreSpeedFromScroll() 执行：
  → 如果 slideSpeedActive 已经是 true（没有进入过慢放），直接返回
  → 恢复 slideSpeedActive = true
  → 如果进入慢放前有手动锁定：
      → 恢复 preManualSpeedLock 和 preManualSpeedValue
      → 速度恢复为之前锁定的倍速
      → 对应按钮高亮
  → 如果进入慢放前没有手动锁定：
      → 恢复常速 500ms
      → 所有按钮不高亮
```

**关键保护**：`restoreSpeedFromScroll()` 开头检查 `if (slideSpeedActive) return;`，防止日志自然滚动到底部时误触恢复逻辑，导致手动锁定的高亮被清除。

**按钮高亮规则（updateSpeedButtons）**

| 条件 | 高亮行为 |
|------|---------|
| `slideSpeedActive === false`（慢放中） | 0.5x 高亮；若之前手动锁定非0.5x，该按钮半高亮 |
| `slideSpeedActive === true` 且有手动锁定 | 锁定按钮高亮 |
| 其他情况 | 所有按钮不高亮 |

**调试模式与非调试模式**：

| 模式 | 显示按钮 |
|------|---------|
| 非调试 | 2x + 0.5x 两个简化按钮 |
| 调试 | 7x / 4x / 2x / 0.5x 四个独立按钮 |

**按钮状态管理（updateButtons）**

**主按钮**（`btnMain`）按游戏状态动态变化：

| 游戏状态 | 按钮文字 | 行为 |
|---------|---------|------|
| IDLE + 调整模式 | "▶ 开始(投票)" | 进入战斗 |
| IDLE + 非调整模式 | "🔄 调整站位" | 站位调整 |
| GAMEOVER + 第6关 | "🔄 重新开始" | 重置全部关卡 |
| GAMEOVER + 非第6关 | "▶ 下一关" | 进入下一关 |
| RUNNING | 禁用 | 不可点击 |

**子弹时间保护**：当 `window.bulletTimeActive === true` 时：
- 暂停按钮：显示"⏸️ 暂停"但**禁用**

### 五、反击风暴修复总结

**问题描述**

闪避反击子弹时间特效中，反击者头顶的反击风暴（旋转光环）完全不可见。

**根因分析**

**1. 环不旋转**：每个 `.storm-ring` 上有内联样式 `transform: rotateX(75deg)`，而 CSS 动画 `stormSpin` 也是通过 `transform` 驱动的。内联样式优先级高于 CSS 动画，导致动画被覆盖，环静止不动。

**2. 旋转轴不对**：`stormSpin` 关键帧里写了 `rotateX(60deg) rotateZ(...)`，导致环在 3D 空间中绕 X 轴翻滚，而不是在压扁的椭圆平面内水平旋转。

**3. 视觉太弱**：环的边框仅 `2px solid white`，无发光，经 `rotateX` 压扁后在深色背景上几乎不可见。

**修复方案**

1. 将 `rotateX(75deg)` 从子元素移到父容器，释放子元素的 `transform` 给动画使用
2. 动画改为纯 `rotateZ`，在已压扁的平面内旋转
3. 边框加粗 + 白光阴影增强可见性
4. 高度压缩（90→40px）使图形更紧凑
5. 清除调试红点

**最终实现**：`createCounterStorm` 函数创建 4 个 `.storm-ring`（3px 白边框 + 发光阴影）挂到父容器，父容器设 `rotateX(75deg)` 压扁，子元素用 `@keyframes stormSpin` 纯 `rotateZ` 旋转。两端加白色锤头小球。完整代码见 `fx/20fx-dodge-bullet.js`。

**S01 - 文件复制器序列发送优化**

**问题描述**：文件复制器点击"序列发送"后，弹窗显示的包序号始终比当前复制的包多一个。

**根因分析**：`nextBatch()` 函数逻辑顺序错误——复制当前包 → sendIndex++ → 显示弹窗，显示的是 ++ 后的下一个包。

**正确方案**：

**优化一：显示当前操作内容**：复制后先显示"已复制当前包"，再 ++ 切换到下一包，等待下一次操作。

**优化二：一键开始，立即复制第一个包**：点击"序列发送"后直接复制第一个包并显示"已复制"，后续每个包按 Enter 复制。

**关键点**：`renderSenderBar(sendIndex, 'copied')` 中，`sendIndex` 必须在复制后立即显示，不要 ++ 后再显示。`nextBatch` 顺序：写入剪贴板 → 显示"已复制" → sendIndex++ → 延迟显示下一包。点击事件直接调 `nextBatch()` 复制第一个包。完整代码见 `tools/32-toolkit.js`。

**核心原则**：弹窗显示的是用户当前正在操作的内容，不是下一个要操作的内容。

**S02 - 格子飞撞（showMeleeCrash）修复后完整逻辑**

**飞撞动画流程（不变）**：蓄力放大(800ms) → 克隆体飞出撞击(900ms) → 弹回原位消失(800ms)，总时长 = 2500ms × speedFactor。两个模式：`'ghost'`（虚影）和 `'fly'`（飞走）。

**修复后的数据流（核心差异）**：

旧框架：特效文件直接操作 DOM（`cellA.style.visibility = 'hidden'`），依赖时序控制。一旦播放器在动画期间触发 `updateUI`，格子就被重绘出来，造成残留。

新框架：改为数据驱动渲染。

1. **飞撞开始**：通过 Store dispatch `SET_VISUAL`，给单位设置 `_flyMode = 'ghost'` 或 `'fly'`，调 `updateUI` 触发重绘。
2. **重绘阶段**：`renderGrid` 遇到 `unit._flyMode` 不为空，跳过正常渲染，直接画占位格。飞走模式空白，虚影模式半透明蓝色。
3. **动画期间**：克隆体在 `body` 上飞行，与 grid 内占位格互不干扰。无论播放器何时调用 `updateUI`，始终画占位格。
4. **飞撞结束**：`finishCrash` 移除克隆体，Dispatch 清空 `_flyMode`，设 `_acted = true`，Dispatch `SET_FLASH: 'attack'`，调 `updateUI` 恢复蓝色闪光。
5. **蓝色闪光保留**：播放器 `atkTimer` 到时间后正常清除 `_flash`。

**播放器侧保护**：`handleAttackGroup` 末尾同步清除闪光加了 `_flyMode` 检查，飞走单位跳过 `SET_VISUAL` dispatch。

**旧框架 vs 新框架对比**：

| | 旧框架 | 新框架 |
|---|---|---|
| 隐藏方式 | CSS 操作 | 数据标记驱动渲染占位格 |
| 重绘风险 | 依赖时序，重绘即残留 | 始终画占位格，重绘安全 |
| 闪光恢复 | 依赖播放器 | finishCrash 主动 dispatch |
| 播放器保护 | 无 | 加 _flyMode 检查 |

**S03 - 闪避反击（子弹时间）修复后完整逻辑**

**触发条件**：防御者成功闪避时，播放器检测到 `entry.isDodge === true` 且开启华丽模式。

**六阶段流程**：闪电(400ms) → 黑幕降临(200ms) → 屏息凝视(3000ms) → 飞撞+碰撞(4000ms) → 气泡+飞走(2000ms) → 清理恢复(200ms)

**旧框架 vs 新框架对比**：

| | 旧框架 | 新框架 |
|---|---|---|
| 格子高亮方式 | 直接修改 dCell 内联样式，仍是 grid 子节点 | 隐藏原始格子，克隆体挂 body，脱离 grid 层叠上下文 |

| 闪光颜色分配 | 反击者误设为蓝色 attack | 反击者设黄色 defend，攻击者设蓝色 attack |

### 七、弹幕/特效消失问题

**问题现象**：第一关正常，第二关及之后所有弹幕、伤害飘字、治疗数字、闪避气泡全部不显示。

**根源**：项目使用对象池机制复用 DOM 元素。弹幕、飘字等元素在创建时被标记了 `data-fx="temporary"` 属性。关卡切换时调用 `clearAllEffects`，删除页面上所有带 `[data-fx="temporary"]` 属性的元素。对象池中的元素就这样被从 DOM 中移除。后续 `acquireFromPool` 虽能拿到 JS 引用，但元素已脱离 DOM。

**修复**：去掉四个对象池创建函数中的 `setAttribute('data-fx', 'temporary')`：

| 函数 | 池类型 | 用途 |
|------|--------|------|
| `createDanmakuEl` | danmaku | 弹幕气泡 |
| `createDmgFloatEl` | dmgFloat | 伤害飘字 |
| `createHealFloatEl` | healFloat | 治疗数字 |
| `createDodgeBubbleEl` | dodge | 闪避气泡 |

这些对象池元素是长期复用的，不应被 `clearAllEffects` 清除。

### 八、倍速按钮逻辑修复

**问题现象**：
- 点击高亮的 2x 按钮无法取消高亮
- 点击 7x 高亮后滚动日志，恢复时变成 2x
- 日志自然滚动也会清除倍速高亮

**第一步**：把 39 里的倍速相关变量删掉，所有状态统一在 44 中维护。

**第二步**：在 44 中实现完整的倍速逻辑。

**变量设计**：

| 变量 | 作用 |
|------|------|
| `manualSpeedLock` | 是否有手动锁定的倍速 |
| `manualSpeedValue` | 锁定倍速的数值 |
| `slideSpeedActive` | 是否正常播放（false = 滚动慢放中） |
| `preScrollSpeed` | 滚动前保存的速度值 |
| `preManualSpeedLock` | 滚动前保存的锁状态 |
| `preManualSpeedValue` | 滚动前保存的锁数值 |

**状态机逻辑**：

```

  ├─ 已高亮 → 取消锁定，恢复 speed=500，所有按钮不高亮

  ├─ 有手动锁 → 恢复原倍速，该按钮重新高亮

日志自然滚动到底部（非用户操作）：
  └─ 不触发任何倍速变化
```

**关键保护**：`restoreSpeedFromScroll` 中 `if (slideSpeedActive) return;` 防止日志自然滚动时误触恢复逻辑。

## 改动汇总：BGM 改为 Web Audio 缓存播放

### 问题

1. BGM 使用 `<audio>` 元素（`new Audio(url)`）播放，依赖浏览器对 `file://` 协议下音频加载的支持
2. VSCode 内置预览、部分移动端浏览器无法正常播放 BGM
3. 攻击音效早已使用 Web Audio API 缓存模式（`fetch` + `decodeAudioData` + `createBufferSource`），BGM 却走不同的通道，架构不统一

### 方案

将 BGM 也改为 Web Audio API 缓存播放，和攻击音效走同一条通道：
- `fetch(url)` 加载音频文件
- `ctx.decodeAudioData(arrayBuffer)` 解码到内存缓冲区
- `ctx.createBufferSource()` 创建播放源，设置 `loop = true` 循环播放
- `GainNode` 控制音量，支持淡入淡出

### 涉及文件

| 文件 | 改动 |
|------|------|
| `modules/28audio-manager.js` | `init()` 改为调用 `loadBgmBuffer()` 预加载 BGM 到内存；`play()`/`pause()`/`setVolume()`/`fadeTo()`/`switchSource()` 全部改为操作 `bgmBuffer` + `bgmGainNode`，不再依赖 `<audio>` 元素；新增 `_playBgm()` / `_stopBgm()` 内部方法 |
| `index.html` | 独立背景音乐逻辑从 `new Audio()` 改为 `fetch` + `decodeAudioData` + `createBufferSource` 的 Web Audio 缓存模式 |

### 效果

- VSCode 内置预览：BGM 正常播放
- 手机端：BGM 正常播放
- 网页端：BGM 正常播放
- 攻击音效和 BGM 统一走 Web Audio API，共享同一个 `AudioContext`，架构一致***********************
