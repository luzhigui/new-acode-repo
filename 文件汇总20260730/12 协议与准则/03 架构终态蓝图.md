# 架构终态蓝图

> 版本 V2.0.0 | 2026-10-25 | 预估约 3.2 KB
>
> 定位：长期目标与当前差距。只讲「终态是什么」和「现在差多远」，**不记历史过程**（历史见 `记录-更改履历.md`）。
> 用法：任何架构改动前，先对照本文档判断方向对不对。

---

## 一、终态一句话

**游戏规则 = 纯数据，引擎 = 唯一执行器，battleStore = 唯一状态，播放器 = 查表调度器，UI/fx = 纯渲染。加一个角色 / 技能 / buff / 海克斯 = 只加数据，不写一行引擎逻辑。**

---

## 二、七条单一化原则

每条都是「入口唯一、出口唯一」——一旦唯一，就没有双轨可收，也没有渐进式挤牙膏。

1. **单一事实源（数据）**：技能、buff、职业、数值、台词全部声明在内容文件里；JS 零规则硬编码、零魔法数字。例外：基础设施常量（格子数、超时时长、动画基准速度）允许在 infra 层集中声明。

2. **单一执行器（引擎）**：状态只有一条写路径「读声明 → 裁定 → `applyStatChange` / `recordCombatStat`」。可声明化的机制走数据声明，复杂机制（状态机/连续选择）走注册处理器，不强行声明化。

3. **单一状态（battleStore）**：battleStore 是运行时唯一主账本；结算结果走事实流单通道写 store，UI/fx 只读 store。引擎 A/B 是模拟期工作区（每回合克隆、算完即弃），**不是第二账本**。

4. **单一调度（查表）**：播放器按 `STAGE_ACTION_DEFS` 读表驱动；factType → stageAction → 格子/特效/日志三线完全由表定义，无硬编码 case。

5. **单一枚举层（infra）**：所有跨层字符串（factType / stageAction / store action / buff type）进枚举，错名即报错。

6. **单一依赖方向**：`infra → core → render/modules → player → ui/fx`，靠 eventBus 信号解耦，无环、无反向。

7. **分层可测**：高风险层（UI 状态复位、时序/结算延迟、特效 DOM 泄漏、buff 落盘）由 `tests/health-rules` 覆盖；行为数值正确性靠声明契约（注册时校验）+ 抽查规则兜底。**加新内容不强制新增规则**。

---

## 三、加内容 = 只加数据

扩展点一次定全，之后加内容走固定通道、不动代码。

| 扩展类型 | 数据通道 | 动引擎代码 |
|---|---|---|
| 加角色 | `gameData.characters.*` + `mechanics` 声明，`core/02 HERO_FLAGS` 一行 + barrel 注册一行 | 否 |
| 加精英出场配置 | `roster.eliteConfigs` / `elitePower` / `eliteRate` / `enemyElitePos` | 否 |
| 加技能机制 | `mechanics` 声明 + 效果解释器注册（处理器放 modules 层） | `core/` 不动；新处理器是 modules 层独立文件 |
| 加 buff | `gameData.buffs.*.effects` 声明 + 处理器注册 | 否 |
| 加海克斯 | 海克斯数据表（permanent buff 声明） | 否 |
| 加台词 | `gameData.taunts` | 否 |
| 加 factType | 枚举 → 契约 → 渲染器 → 翻译器，固定模板链 | 是「机械套模板」，非「手写新逻辑」 |

**判断标准：加一个新角色，如果还要改 `core/`、`player/` 里的逻辑，说明骨架没到位。**

## 四、当前差距

按原则列，按影响面排序。每条都指向具体文件/函数，不是空话。

### 原则 2（单一执行器）—— 最大的未完成项

- **`core/11battle-round.js` 的 `applyTeamRoundBuffs` 显式列举 6 个 `apply*Bonus` 调用**（圣火令 / 严阵 / 摄魂 / carry / 背水 / 众志）。加新海克斯必须改 `core/11` —— 违反「引擎不认英雄」。
- **`core/04buff-system.js` 的 `installBuffMechanics` 用硬编码 processors 表**分发 buff 效果（`bloodthirstLeech` / `hotBloodHeal` / `windAssaultSplash` / `meteorShowerMain` / `mindControlSwap` / `holyFireRevive`）。加新 buff 效果必须改这个表。

两处是同一个问题的上下半场：回合开始的 buff 施放没有注册面，buff 效果的处理器也没有注册面。

### 原则 1（单一事实源）—— 两处硬编码

- **`modules/29battle-init.js` 的 `if (currentStage === 5 && xuanmingPairCount === 2)`**：第 5 关玄冥二老齐出的补员规则写死在代码里。
- **`ui/79hanlisa-aim.js` 的 `HIT_MAP` 与 `content.xuLi.hitShapes` 是两份数据**：改命中形状要同时改两处，漏一处黑幕与引擎就不同步。

### 原则 3（单一状态）—— 双轨未收敛

- **`selectOrStore(ctx, 'allyTeam' | 'enemyTeam')`** 在 `render/32`、`ui/62`、`player/42`、`player/45`、`player/46`、`player/49` 里仍是「store 优先，回退 `c.UI`」的双轨。战斗期 store 必然存在，回退分支是历史包袱。
- **`c.snapshot` 与 `battleStore` 在开战瞬间并存**：`ui/61 startBattle` 冻结 `c.snapshot`，`player/42 playBattle` 另建 `battleStore`，两份都是完整队伍数据。

### 未成文但已现形的债

- **「可行动」判据没有单点**：`alive` / `hp > 0` / `_pendingDeath` / `_stunned` / 飞天 / 附身这套组合，散在 `core/10` 攻击入口、`core/11` 候选池与循环条件、`core/16` 各 handler、`render/34`、多个精英组件里。最近修的「0 血单位出手」是补了三道防线才拦住——那是症状，病根是判据没有单点化。
- **六大派精英数据化只做了一半**：明教走 `roster.eliteConfigs`，六大派仍分散在 `encounters.elitePool` 和 `roster.enemyM` 两处，格式也与明教不同。

## 五、验收标准

1. 全库搜索无裸字符串 `factType` / `stageAction` / `store action`。
2. `Unit` 顶层无 `_` 开头的临时状态字段；`_initAtk/_baseDef` 等属性快照属合理留驻。
3. 新增一个带新机制的虚构角色（如反伤护盾），只加数据 + 在 modules 层新增注册处理器；`git diff core/` 为空。
4. 高风险层（UI 复位 / 时序 / 特效 DOM / buff 落盘）的 failure 路径在 `tests/health-rules` 有对应规则。
5. 依赖方向上无循环、无反向 import。
6. **加一个新海克斯，不改 `core/04` 和 `core/11`。** 这是原则 2 目前唯一未达成的尺子，达成后原则 2 才算闭环。
