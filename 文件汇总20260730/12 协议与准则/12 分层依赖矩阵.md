## 一、判据真源（不新造）

| 出处 | 原文 |
|---|---|
| `09 架构铁律12条.md` 第 6 条 | **交互链路单向**：`ui/fx → player → render/modules → core → infra`；跨层通信走 `GlobalStore` + UIHandler 通道，禁止反向 import，禁止 window 桥。 |
| `03 架构终态蓝图.md` 原则 6 | **单一依赖方向**：`infra → core → render/modules → player → ui/fx`，靠 eventBus 信号解耦，**无环、无反向**。 |

两份文档的链是同一根，只是书写顺序相反。本矩阵统一取「箭头 = 依赖流向」的读法，等价展开为 rank：

```
rank 0  infra               地基
rank 1  core                引擎
rank 2  modules-mechanic    机制（26/27/28/29 等）
rank 2  modules-facility    表现设施（22 音频 / 21 错误面板）
rank 3  render              渲染
rank 4  player              播放器
rank 5  ui / fx             最高层（并列）
rank 6  tools               链外旁支（离线工具、打包器）
rank 9  tests / scripts     观察者（豁免）
```

**为什么 modules 要二分**（保持 rank 不变，只切语义）：
`modules/` 里同时住着两类东西——`26/27/28/29` 是引擎机制，`22audio-manager` 是纯表现设施。混居会让「render → modules」看起来像越界，实际 render 依赖音频是合法的向下依赖。二分后语义清楚，rank 仍是 2，不影响任何判定。

**为什么 tools 是「链外」而不是最高层**：
工具（`tools/52` 生涯记录、`tools/107` 日志查看器、`tools/106` 打包清单）本就不在运行链上。它们可以读全仓（这是工具的特权），但**链内任何层都不得依赖它们**——否则链上代码就绑定了离线工具，工具一改就炸运行时。

## 二、两类判据（分开报，别混成一句「越界」）

**A 类 · 反向依赖**：`rank(from) < rank(to)`，即下层 import 上层。
> 例：`render(3) → fx(5)` 是渲染层反向依赖特效层。

**B 类 · 循环依赖**：层图上的强连通分量（SCC）含 ≥2 层。
> 环里每一条边单看都可能朝下（合法的），但**两个方向同时存在就成环**。ESM 成环会踩「求值顺序 → 拿到 undefined」，加载顺序一变就炸，且往往表现为间歇性 bug。这就是 03 原则 6 里「无环」三个字的落地判据。

分开报的理由：A 类的修法是「删/反转某条 import」；B 类的修法是「二选一保留一条通道」。混在一起会让人以为都是同一类活儿。

## 六、待用户拍板的两件事

**① fx 到底在 player 之上还是之下？**

- 铁律第 6 条说 `ui/fx → player`：fx 在**上**，靠 eventBus 信号订阅 player 的事件。
- 实现说 `player/41`、`player/46` 直接 import fx 来播：player 在**上**。
- A2/A3/A4 三条反向边全部源于这个矛盾。

两条出路，二选一：
- **(a) 以铁律为准**：player 改发信号，fx 订阅后自己播。改动面：player/41、46 三处调用点 + fx 侧订阅注册。收益：铁律成立，特效可独立开关。
- **(b) 以实现为准**：承认「player 驱动 fx」，把铁律第 6 条改写为 `ui/fx → player` 中 fx 在 player **之下**（即 `ui → player → fx → render`）。改动面：改 1 行文档。代价：fx 不再是可独立订阅的层，「特效函数只出现在播放器层」（第 9 条）也随之要重写。

我倾向 (a)，因为第 9/10 条本来就是按「player 驱动特效」写的，而 (b) 会让这两条失去依据；但 (a) 要动三处播放器代码，属于主代码改动，等用户点头。

**② 本文件与扫描器何时转正？**

## 八、附：反向引用查询（搬 79/80 的依据）

搬家需要的不是「越界清单」，而是「谁引用了我」。同一解析器的第二种输出，一次覆盖三类引用点：

```bash
$ node tests/layer-direction-scan.mjs --refs ui/79hanlisa-aim.js
  JS import / re-export：1 处
    ui/65main-battle.js:18  (side-effect)
  HTML <script>/<link>：0 处
  tools/106 打包清单：1 处
    tools/106-ai-pack-config.js:67  '../ui/79hanlisa-aim.js',
  ── 合计 2 处引用点

$ node tests/layer-direction-scan.mjs --refs ui/80perf-panel.js
  JS import / re-export：0 处
  HTML <script>/<link>：1 处
    index.html:404  <script type="module" src="./ui/80perf-panel.js?v=3.5.1"></script>
  tools/106 打包清单：1 处
    tools/106-ai-pack-config.js:69  '../ui/80perf-panel.js',
  ── 合计 2 处引用点
```

结论：**79 与 80 各 2 处引用点**，且 80 的入口在 HTML（带 `?v=` 缓存串，扫描时已剥除后比对）。
只做 JS import 反查会得出「80 无人引用」的错误结论——这正是搬家最容易漏的一类。

两类引用点的性质不同（也印证了上一轮的判断）：
- **79 是静态 import**（挂在 `ui/65` 上），搬家改路径即可。
- **80 是入口脚本**（`index.html` 的 `<script type="module">`），除改路径还要处理「80 顶层就 `setUIHandler('openPerfPanel')`」的加载时序，不是纯字符串替换。

清单侧另有一道自动防线：`tests/pack-manifest-check.mjs` 会对「106 清单指向磁盘不存在的文件」告警，搬家漏改清单会被它抓到。
