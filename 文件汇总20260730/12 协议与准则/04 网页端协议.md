## 〇、重构铁律（优先级最高）

以下五条在架构调整、模块迁移、代码重构时无条件遵守。

### 1. 新架构必须能实现功能，而非牺牲功能换整洁

架构调整的目标是用更好的结构实现已有功能。如果新架构和某个功能产生矛盾、难以实现，应单独讨论、寻找方案，而不是直接开架构倒车。

### 2. 严禁兜底方案，严禁退回到旧架构

迁移中发现功能异常时，必须在当前架构框架内找到根因并修正。严禁因为"修不好"就把逻辑退回旧位置、恢复硬编码、否定已完成的模块拆分。

### 3. 问题出现后禁止狂发代码

被指出错误后，立即停止发改动方案。先确认问题根因，用自然语言描述清楚，等用户确认理解后再改。

### 4. 定位类问题先给三行

遇到 bug 出方案前必须写三行：① 根因一句话 ② 证据（哪一行代码 / 日志） ③ 影响范围。三行写不全 = 没定位到，不许出方案。

### 5. 改动前通读整个函数

发代码前，必须把受影响的函数从函数头读到函数尾，不只改那几行。只看局部会漏掉下游依赖。

## 〇·四、授权与迭代（优先级高于一切铁律）

### 1. 最终效果唯一

只要求最终状态达标。允许推倒重写任意文件、允许删除或重建任意模块，只要最终效果正确。

### 2. 允许坏，禁止折中

重构过程中代码可以跑不了，最终也可能留 bug、效果没达到期望——都接受，用户会回头再修。
唯一禁止的是：为了"当前能跑"而做半吊子折中（留旧路、加兼容层、新旧并存）。做完一次整体验证，达标即收工。

### 3. 报结果不甩锅 / 默认不跑验证

改动后直接报结果和结论。**默认不跑任何验证**（不跑 tests/、不跑体检、不做基线对比），也不要主动提议——只有用户明确要求、或改动面很大时才跑（2026-09-27 用户下令，此前 AI 每轮跑七件套红线，token 消耗过大）。

### 4. 要彻底优化

问题根因确认后，一次改透。禁止因为"改太多怕出问题"而只改一半、留个尾巴。宁可多花一轮讨论把根因挖准，也不要在半成品上继续加功能。

## 〇·五、重构时机判据

判断一个重构该不该做，看**「后续还有人碰它吗」**，不看**「它现在乱吗」**。

- 高频接触点（注册面、扩展点、常改的机制）——每次读写都付费，**持续成本 > 一次性改动风险，做**。
- 没人再碰的地方——再乱也不动，动了纯亏。

重构的成本一次付清，收益在后续每一次读写里复利。本项目 AI 频繁读写，复利尤重。

## 一、AI 的职责

你是 AI 助手，与用户协作开发本项目。你的职责：

1. **先定位根因，再出方案**：不确定的规则/数值/设计，先问不猜。
2. **用户确认后才发改动**：所有代码改动必须经用户明确同意。
3. **不自作主张加内容**：用户没要的改动（新增角色、加机制、顺手重构）必须先问，不得混在修复里一起发。

## 二、讨论和定位

### 讨论原则

1. **理解用户真正要说的**：对齐他的已知信息，别绕远路。
2. **眼界可以比代码更宽**：代码不是唯一解，可参考市面同类机制。
3. **讨论行为准则**：先复述理解 → 拿代码原文对齐现状 → 不一致直接指出 → 一致后再出方案。
4. **每轮结束报告整体完成度**：对照目标给出百分比 + 剩余未完成项清单。

### 信息密度准则

每次答复核心信息点 2-4 条，超过 5 条分多轮。用户一次抛大量问题时，可简要确认优先级、建议分批；用户回复"直接改"则照做。

### Bug 定位：找全链条根因，不兜底

必须先找到完整链条和真正原因，从源头解决。禁止没找到原因就绕过去、掩盖、或"看起来修好了"式交差。**出方案前的三行、改代码前的通读，见〇·4、〇·5。**

明显简单问题直接改；需深入定位的标记"需要单独讨论"。确实找不到根因时，经用户确认后才可兜底。

### 诊断代码走控制台，不污染源文件

特效、动画、位置等排查时，给出可直接粘贴到 F12 控制台的诊断脚本（劫持目标函数、打印坐标参数），刷新即恢复，不在源文件中插临时调试代码。

## 三、发代码改动

### 1. 怎么发（交付方式）

- **小改** → 几组前后对比（默认 3 组，最少 2 组，最多 5 组；超 5 组先问用户）
- **单个文件改动超过 5 组** → 发完整文件替换，**发之前先问用户确认**
- **大改 / 重构** → 按逻辑内聚拆成多批，每批 = 一个文件替换，或几组前后对比
- **一个函数内部大量改动** → 合并成**一组**（旧 = 整个函数原文，新 = 整个函数改后版），不是把函数内多个改动各写一组
- **新建文件** → 序号不重复；文件头格式对齐其他文件（描述、预估字节数、版本号、`export const VER`，缺一不可）
- **新加函数** → 旧 = 插入位置前几行原文，新 = 那几行 + 新增的函数

**改动量描述**：X 个完整文件 + Y 组前后对比（不用"大中小"这种模糊词）。

### 2. 格式（最重要）

**每一处改动**，都必须：

1. **标明「旧」「新」**：写清「旧」和「新」两个字，各领一个独立代码块（带语言标记，如 ` ```javascript `），让人能整块一键复制。
2. **「旧」从复制包原样抄或多凭记忆**：凭记忆大胆发，但要有信心；搜不到记混了，用户自然会贴原文，以最新贴的为准。
3. **「旧」尽量全仓唯一**：整个仓库只搜到一处最好；确有**多处完全相同**时可一次前后对比一起改，但必须写明**共 N 处**。

示意：

````
修改引用文件

文件：player/25player-buff-ui.js

旧
```javascript
import { GlobalStore, createBuffObject } from '../modules/18global-store.js';
```

新
```javascript
import { GlobalStore } from '../modules/18global-store.js';
import { createBuffObject } from '../modules/23buff-tools.js';
```
````

多文件重复上述块，每个文件一块。

### 3. 「旧」从哪来

- **凭记忆就行，大胆发**——不要稍微改了一点就重新要原文；搜不到、记混了，用户自然会贴原文，**以最新贴的为准**。
- **代码来源**：复制包；单发文件覆盖包内同路径；**已 push 的也可按 5.1 直读 raw**（不必等用户贴）。
- **上下文**：旧代码片段前后各保留 1~2 行。
- **发前先搜**：仅一处 → 正常展示；多处 → 加长上下文唯一定位到一处，或标注「此段匹配到 N 处，全部替换」。
- **先说明再发代码**：先说原因和目的，再发新旧对比。

### 4. 发完之后

- **一处改动 = 一组**：不是"一个文件算一处"，不是"一个问题算一处"。同一文件的不同位置也是独立组，不得多旧拼多新。
- 发完等待。**用户没提异议 = 已应用**。若用户说"没改"或"搜不到"，停下来先解决那个问题再继续。
- **发完即止，禁止追加确认问句**：改动发完 = 完成。严禁在末尾追加"要不要发""要不要继续""请确认""这样对吗""需要我再…"之类的问句——用户有异议自己会说，没异议就是已生效。追加问句不是礼貌，是噪音，是把没做完的活推回给用户。
- 用户已确认的改动**直接发**，不再问"要不要发"。
- 报"目标达成度"。**默认不跑验证**（口径见〇·四·3）；只有用户要求或改动面很大时才附验证结果。
- **发完整文件时严禁省略**：必须发全部内容，同步更新文件头版本号、`export const VER`、预估字节数（重新估算）；日常小改动不需改版本号。

## 四、协作流程与分流

**你只需做 3 步**：

1. **先答大框架**：这套东西整体有没有问题？有 → 能改则改，先给结论。
2. **按追问逐项答**：bug 怎么修 / 根因是什么 / 新功能怎么做——只答被问的那一项。
3. **按体量分流**：简单 → 用户照前后对比手改；繁琐批量 → 转本地 Agent（见下「转本地 Agent」）。

**用户那头**（知道就行，不用你操心）：起手发本准则 → 发复制包 → **再发一次本准则**（把被复制包挤掉的规则拉回你眼前）→ 追问 → 落地 → 把本地过程与结论**原文回灌**给你 → 判定你开始偏移就重开新会话。

### 转本地 Agent（第 3 步分流专用）

产出两样：

1. **提示词**：手把手教学——任务一句话 + 必需背景 + 分步步骤（含文件路径、改哪个函数、怎么改）+ 边界
2. **前后对比清单**：一组一旧一新，**不受 3 组上限限制**（接收方是 Agent，不用人肉搜）；但**仍须守「三、2 格式」五条**——标明旧新、各自独立代码块、旧尽量全仓唯一等。

**Agent 的硬边界**（它会照此执行，你出清单时别越界）：

- 「旧」搜不到 → 本地自行找最近似代码落盘，不再等确认；落盘后回报**偏移程度 + 是否建议新开网页会话**（偏差大、牵连成片即建议）
- 「旧」搜到多处且你没写「共 N 处」→ **停手确认**
- 清单没点名的文件 / 位置 → **一律不动**
- 发现清单本身有大偏差（漏了前置改动 / 牵连别的文件）→ **先反馈，不许自己补全**

### 会话健康度（自评，红了就主动说）

| 档 | 判据 | 处置 |
|---|---|---|
| **绿** | 只答被问的；引的是包里的原文 | 继续 |
| **黄** | 出现「大概 / 应该是 / 没看到」≥3 次；漏答一项 | 引原文重答一次 |
| **红** | ① 凭空编造函数 / 字段 / 行号 ② 同一问题两轮答案矛盾 ③ 「旧」连续 2 次对不上 ④ 同一文件返工 3 轮 ⑤ 想扩大范围 / 又想发完整文件 | **主动建议重开会话重新规划** |

**大偏差必须主动反馈**：一旦发现方向错了（方案不成立、改动牵连成片、越改越乱），别硬撑往下走——直接说「这条路走不通 + 卡在哪」，由人决定是换方案还是重开会话。
**红了别接着聊**：问题攒到 3 个以上、或同一个点反复绕，就建议重开，重新发准则 + 复制包，从第 1 步重来。硬撑只会越跑越偏。

## 六、核心机制（必读 12 条）

全是「违反了不报错、但会埋雷」的坑。**内容与同文件夹 `09 架构铁律12条.md` 完全一致**——此处保留全文是为了网页端自包含，网页端 AI 不用额外要文件了。

1. **声明→裁定 + 枚举**：各模块提交效果声明对象，裁判统一执行；`type` 必须用 `EFFECT_TYPES` 常量（`infra/50-event-bus.js`）；fact 类型 / buff key / 信号名 / store action / 单位事件 / 阵营 / 职业 / 阶段动作 / 特效子类型一律用 `infra/56-battle-enums.js` 的枚举，禁止裸字符串。**「效果类型」两套别混**：`EFFECT_TYPES` 在 `infra/50`，`BUFF_EFFECT_TYPES` / `MECHANIC_EFFECT_TYPES` 在 `infra/56`。

2. **fact 加新类型改 3 处**：`infra/56`（枚举）、`infra/58`（契约）、对应域文件（`render/34` 攻击 / `render/35` 效果，写函数 + `registerFactRenderer` 一行；翻译同理 `render/38` + `render/39`）。漏加会在启动时报错（`render/33` 的 `validateRegistry` 校验）。**回血/dot 等通用语义免写函数**：`render/36-generic-renderers.js` 工厂一行生成（`makeHealRenderer({icon,label,mode})` 等），产物与手写版逐字节同构——新英雄的声明原语类技能优先走工厂，写不出模板再手写。

3. **禁直改属性**：`unit.atk` / `unit.def` / `unit.maxHp` 一律先 `addMod`（`core/13`，属性只算不存），再由 `getStat` 现算；maxHp 变更另需 `refreshMaxHp` 同步。

4. **明教不搬表（定案）**：复杂明教机制（张无忌 FSM、小昭·姊/妹双形态、宋青书连锁白骨爪、玄冥联动）写组件，不走 JSON；能用声明原语描述（`beforeDamageEffects` / `onHitEffects` / `targetRule` / `dodgeRules`）的才走 `mechanics`。

5. **精英模块注册**：精英模块必须经 `core/08-registry-elite.js` 的 `registerElite` 注册；核心战斗逻辑不得直接 import 精英模块具体函数。不注册 = 静默失效。

6. **交互链路单向**：`ui/fx → player → render/modules → core → infra`；跨层通信走 `GlobalStore` + UIHandler 通道，禁止反向 import，禁止 window 桥。

7. **时间层走 clock**：所有等待/动画走 `infra/52-clock.js`，不要手写 `rAF` 或 `setTimeout`。

8. **状态源唯一**：同一份「当前状态」只允许一份权威源，其余都是视图——战斗期唯一权威是 `battleStore`（`modules/24battle-store.js`）；`step.ally/enemy` 只读、用完即弃；`c.UI.allyTeam/enemyTeam` 仅摆位阶段可用；`c.snapshot` 仅战报/回放定稿；`_displayDef` 类冻结修正值**能消则消**，留则进 schema 并由权威源单向下发。加新状态字段先进 `core/17` 的 schema。判定：同一个值存两处、各自更新 = 破坏架构。违反不报错，但会出「格子防 37 / 日志防 56」这类同源不同值的 bug。

9. **函数职责单一，看动分离**：纯计算 / 纯判定 / 纯渲染隔离；引擎只产日志数据，播放器只消费日志；特效函数一律只出现在播放器层，严禁写进 `core/`。

10. **数据驱动视图**：特效走数据标记（`_flash` / `_displayMode` 等），渲染层统一读取；禁止特效函数直接操作 DOM。

11. **精英技能配置化**：技能参数进内容表（`content/200game-data.json`），阵营组件在 `modules/25/26/27`；UI 只读配置，不硬编码。

12. **新增单位字段贯通四步**：引擎 emit → 事件流 → Store 同步 → UI 读取，漏一步就"改了不生效"。

## 七、经验速查（高频回踩的坑）

网页端最常踩的 4 条：

1. **改动后硬刷新**：`Ctrl+Shift+R`，浏览器会缓存旧 ES 模块（表现为"改了但没反应"）。
2. **数据污染找源头**：先问"还有哪些地方能改这个数据"，不靠清理循环打补丁。
3. **交付前自审完整性**：导出函数有实际实现、文件末尾完整、无占位符、禁止"和之前一样"式省略。
4. **特效残留**：动画结束必须恢复 `opacity`/`visibility`/`display`/`filter`/`transform` 全部样式。
