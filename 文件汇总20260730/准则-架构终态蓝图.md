# 架构终态蓝图

> 定位：**长期目标**，非当前状态快照。这份文档回答"最终长什么样"，作为后续所有架构改动的对照基准。
> 前提：项目内容会持续增加（新角色、新机制、新海克斯、新玩法），因此终态不是"把现有东西收敛死"，而是"**扩展只走数据通道，不碰引擎代码**"。
> 版本: V1.6.0 | 2026-08-26 建立 | 2026-08-28 二次评审校正②b方向 + 进度同步 | 2026-08-28 三次评审：**放弃种子基线**（当前无意义）+ 四项批判修订（原则7分层验证、契约注册时校验、②b action 白名单、零魔法数字例外清单）

## 一、终态一句话

> 目标：用一句话锚定全项目终态，所有改动先对这句话。
> 现状：方向已定，与现状的具体差距见第四节路径。

**游戏规则 = 纯数据，引擎 = 唯一执行器，battleStore = 唯一状态，播放器 = 查表调度器，UI/fx = 纯渲染。加一个角色 / 技能 / buff / 海克斯 = 只加数据，不写一行引擎逻辑。**

## 二、七条单一化原则（终态形态）

> 目标：收敛"入口唯一、出口唯一"，杜绝双轨。
> 原因：双轨一旦存在就会渐进扩散（挤牙膏），只有唯一化才能根治；其中 2/3 是"正在撞的墙"，4/5 已落地。
> 现状：4（查表调度）、5（枚举层）已落地；2 已迁完、待门槛实验；3 补漏补丁已删（0f22838），剩 SYNC→事实流一步；1/6/7 为长期约束。

每条都是"入口唯一、出口唯一"的极致——一旦唯一，就不再有"双轨"可收，也就不再有渐进式挤牙膏。

1. **单一事实源（数据）**：技能、buff、职业、数值、台词、AI 选择全部声明在内容文件里；JS 零规则硬编码、零魔法数字。**例外清单**：基础设施常量（格子数、超时时长、动画基准速度等）允许在 infra 层集中声明，不属于魔法数字，尺子据此量绿。
2. **单一执行器（引擎）**：状态只有一条写路径「读声明 → 裁定 → `applyStatChange` / `recordCombatStat`」；精英模块保留状态机类机制的载体地位；可声明化的机制一律走数据声明，复杂机制（状态机/连续选择）走注册处理器，不强行声明化。
3. **单一状态（battleStore）**：battleStore 是运行时唯一主账本；**结算结果走事实流单通道写 store，UI/fx 只读 store**。引擎 A/B 是模拟期工作区（每回合从 state 克隆、算完即弃），**保留不拆**——它不是第二账本，是防回合中途状态污染的保险；要消灭的是"逐字段镜像同步"这个动作（SYNC 镜像/补漏补丁），不是这份数据。
4. **单一调度（查表）**：播放器按 `STAGE_ACTION_DEFS` 读表驱动；factType → stageAction → 格子/特效/日志三线，完全由表定义，无硬编码 case。
5. **单一枚举层（infra）**：所有跨层字符串（factType / stageAction / store action / buff type）进枚举，错名即报错。
6. **单一依赖方向**：infra → core → render/modules → player → ui/fx，靠 eventBus 信号解耦，无环、无反向。
7. **分层可测（V1.6.0 修订）**：不再要求"每种 factType 配回归规则"（与新内容=纯数据通道自相矛盾，给扩展背测试债）。改为**分层验证**：高风险层（UI 状态复位、时序/结算延迟、特效 DOM 泄漏、buff 落盘）由 tests/health-rules 规则覆盖；行为数值正确性不强制全量规则，靠声明契约（注册时校验）+ 抽查规则兜底。加新内容不强制新增规则。

## 三、加内容 = 只加数据（一步到位的落点）

> 目标：扩展点一次定全，之后加内容走固定通道、不动代码。
> 现状：角色/技能/buff/海克斯已有数据通道；factType 走固定模板链；具体缺口见第四节路径。

"一步到位"指的是**扩展点一次定全**，之后加内容走固定通道、不动代码：

| 扩展类型 | 数据通道（只加数据） | 是否动引擎代码 |
|---|---|---|
| 加角色 | `gameData.characters.*` + `mechanics` 声明 | 否 |
| 加技能机制 | `mechanics` 声明 + 对应效果解释器注册（处理器放 modules 层） | core/ 永远不动；新机制处理器作为 modules 层独立文件插卡 |
| 加 buff | `gameData.buffs.*.effects` 声明 | 否 |
| 加海克斯 | 海克斯数据表（permanent buff 声明） | 否 |
| 加台词 | `gameData.taunts` 数据 | 否 |
| 加 factType | 枚举 → 映射表 → 渲染器 → 回归规则，一条固定链路 | 是"机械套模板"，非"手写新逻辑" |

**判断标准：加一个新角色，如果还要改 core/、player/ 里的逻辑，说明骨架没到位；如果只改内容文件 + 走一条既定的注册模板，说明到了。**

离终态的差距与路径分四步，每步"零行为变化 + 可验证"，步步为营：

## 五、验收标准（什么叫"到了"）

> 目标：给"终态达成"定义机器可判的尺子。
> 现状：1/4/5 可 grep/依赖检查判定；2 已达成（属性快照合理留驻）；3 作为 ②a 门槛待跑。

1. 全库搜索无裸字符串 factType / stageAction / store action。
2. `Unit` 顶层无 `_` 开头的临时状态字段，状态全部查表分层；机制状态已迁完，剩余 `_initAtk/_baseDef` 等为属性快照，界定为**合理留驻**（非临时状态），尺子据此量绿。
3. 新增一个带新机制的虚构角色（如反伤护盾），只加数据 + 在 modules 层新增注册处理器；git diff core/ 为空（core 只当框架和注册表，不放具体机制）。普通角色纯填表是下限，不是终态尺。
4. 高风险层（UI 复位/时序/特效 DOM/buff 落盘）的 failure 路径在 tests/health-rules 有对应规则（分层验证，见原则 7），改动被机器校验。
5. 依赖方向上无循环、无反向 import。
