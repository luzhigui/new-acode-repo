# 架构终态蓝图

> 定位：**长期目标**，非当前状态快照。这份文档回答"最终长什么样"，作为后续所有架构改动的对照基准。
> 前提：项目内容会持续增加（新角色、新机制、新海克斯、新玩法），因此终态不是"把现有东西收敛死"，而是"**扩展只走数据通道，不碰引擎代码**"。
> 版本: V1.0.0 | 2026-08-26 建立

---

## 一、终态一句话

**游戏规则 = 纯数据，引擎 = 唯一执行器，battleStore = 唯一状态，播放器 = 查表调度器，UI/fx = 纯渲染。加一个角色 / 技能 / buff / 海克斯 = 只加数据，不写一行引擎逻辑。**

---

## 二、七条单一化原则（终态形态）

每条都是"入口唯一、出口唯一"的极致——一旦唯一，就不再有"双轨"可收，也就不再有渐进式挤牙膏。

1. **单一事实源（数据）**：技能、buff、职业、数值、台词、AI 选择全部声明在内容文件里；JS 零规则硬编码、零魔法数字。
2. **单一执行器（引擎）**：状态只有一条写路径「读声明 → 裁定 → `applyStatChange` / `recordCombatStat`」；精英模块退化为空壳占位，机制 100% 声明化。
3. **单一状态（battleStore）**：运行时唯一可写状态；引擎 A/B、c.UI、玩家副本全是只读派生快照，无双轨。
4. **单一调度（查表）**：播放器按 `STAGE_ACTION_DEFS` 读表驱动；factType → stageAction → 格子/特效/日志三线，完全由表定义，无硬编码 case。
5. **单一枚举层（infra）**：所有跨层字符串（factType / stageAction / store action / buff type）进枚举，错名即报错。
6. **单一依赖方向**：infra → core → render/modules → player → ui/fx，靠 eventBus 信号解耦，无环、无反向。
7. **每规则可测**：每种 factType 在 tests/health-rules 有回归规则 + 对应架构决策文档，改动被机器校验。

---

## 三、加内容 = 只加数据（一步到位的落点）

"一步到位"指的是**扩展点一次定全**，之后加内容走固定通道、不动代码：

| 扩展类型 | 数据通道（只加数据） | 是否动引擎代码 |
|---|---|---|
| 加角色 | `gameData.characters.*` + `mechanics` 声明 | 否 |
| 加技能机制 | `mechanics` 声明 + 对应效果解释器注册 | 解释器是固定模板，非手写逻辑 |
| 加 buff | `gameData.buffs.*.effects` 声明 | 否 |
| 加海克斯 | 海克斯数据表（permanent buff 声明） | 否 |
| 加台词 | `gameData.taunts` 数据 | 否 |
| 加 factType | 枚举 → 映射表 → 渲染器 → 回归规则，一条固定链路 | 是"机械套模板"，非"手写新逻辑" |

**判断标准：加一个新角色，如果还要改 core/、player/ 里的逻辑，说明骨架没到位；如果只改内容文件 + 走一条既定的注册模板，说明到了。**

## 四、当前差距 + 落地路径

当前处于 V5.7.12（六大收敛刚落完），离终态的差距与路径分四步，每步"零行为变化 + 可验证"，步步为营：

| 阶段 | 内容 | 完成标志 |
|---|---|---|
| ① 收尾双轨 | 4 个尾巴：特效单轨碎片、BUFF_TYPES 枚举、Unit 顶层 `_` 字段删净、DEFS 驱动调度 | 全库 grep 无裸字符串、无双轨残留 |
| ② 骨架到位 | 补全所有扩展槽位清单（枚举/查表/唯一入口/数据声明），逐项对照第三节表 | "加内容=加数据"判断标准跑通一次 |
| ③ 内容走数据 | 后续加角色/技能/海克斯严格只走数据通道，反向验证骨架够不够 | 新增内容全程零引擎代码改动 |
| ④ 稳定回归 | 内容达规模后整体回归，修正蓝图不达预期的部分，更新本文档 | 蓝图与实际架构一致 |

节奏原则：**奔着终态直接冲，呈现好效果后，对不达预期的再做调整**——不是边玩边优化，是"目标先行、落地验证、偏差回修"。

## 五、验收标准（什么叫"到了"）

1. 全库搜索无裸字符串 factType / stageAction / store action。
2. `Unit` 顶层无 `_` 开头的临时状态字段，状态全部查表分层。
3. 新增一个虚构角色，能全程只加数据完成，不碰 engine/player 逻辑。
4. 每条 failure 路径在 tests/health-rules 有对应规则，架构决策文档有对应条目。
5. 依赖方向上无循环、无反向 import。
