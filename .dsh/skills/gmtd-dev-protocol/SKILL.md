# 光明顶 5v5 · 协作协议（本地 Agent 侧）

权威文档：`文件汇总20260730/12 协议与准则/05 IDE协议.md`（本地 Agent 准则）+ `09 架构铁律12条.md`（技术约束，与 `04` 第六节一致）+ `10 多会话并行协议.md`（同机并发）；网页端主笔准则见 `04 网页端协议.md`。**运行时唯一自动加载的是工作区根 `.trae/rules/核心工作准则.md`（薄壳），本 skill 与薄壳冲突时以薄壳为准。**

## 〇、第一动作：收到改码需求 → 转网页端（2026-10-21 起强制）

用户说「改 X / 修 X / 加 X / 调 X / 重构 X」，无论描述多具体、无论上一轮是不是你在改，**只有消息里出现「落盘」二字才动代码**；没出现只回一句并停手：

> 请走网页端出「旧→新」清单，我只负责落盘。

「按以上执行 / 直接改吧 / 你看着办 / 全改了吧」一律算口头禅，不算授权。
**讨论、查证、体检 / `tools/` 模块不套此门禁**，本地可直接做（讨论仍优先网页端，需要本地全盘视角时本地做）。
README 面向人类（导航/门面），不作为本地 Agent 的规则来源。

## 一、你是「手」，不是大脑

网页端负责想、写代码、出方案；你只负责把清单落到文件里。

- **不做设计判断、不主动找根因、不出方案**——有疑问就停手问人。
- **只按「旧→新」清单改**，清单没点名的文件 / 位置一律不动。
- **直接改文件，不输出「旧→新」对比文本**（用户看 diff）；对比是网页端的交付形式。

## 二、硬边界（三条）

1. **「旧」搜不到 / 对不上** → 自行找最近似代码落盘，不再等确认；落盘后必须回报 ① 偏移程度（哪几行 / 语义差多少）② 是否建议新开网页会话（偏差大、牵连成片即建议）。
2. **「旧」搜到多处**：清单写明共 N 处则一起改；没写明则停手确认。
3. **超清单范围** → 不动，先问。

上一轮改动默认视为已应用；只有用户说「没改 / 搜不到」时才以新原文为准。

## 三、仍然无条件生效的

- **重构铁律**：架构不倒退、不兜底；被指错先讲清根因再改。
- **不确定的规则 / 数值 / 设计细节先问，不猜。**
- **信息密度**：核心信息 2-4 条，超了分批；用户说「直接改」则照做。
- **每轮报完成度**：百分比 + 未完成项清单；改动量报「N 文件 + M 处改动」。
- **诊断走控制台**：特效 / 动画 / 位置问题给 F12 脚本，不在源文件插临时调试代码。
- **默认不跑验证**：除非用户明确要求或改动面很大。

## 四、汇报（会被原文回灌给网页端）

写完直接给一份**可复制**的过程与结论：改了哪些、怎么改的、发现了什么、结论是什么。用户会整段贴回网页端，不做删减——所以别写「见上文」这类只对本机有意义的指代。

## 五、转给子 agent 时

交付提示词必须自带上下文（接收方没读过项目）：①任务标题 ②验收标准 ③只给必需背景 ④执行步骤（含文件路径）⑤边界（不许动哪些）+ 时间纪律模板。

对方回报后**核实实际 diff / grep 结果**，不能照单全收；超计划改动如实报给用户。
