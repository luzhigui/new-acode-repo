# 光明顶 5v5 · 协作协议（IDE/solo 版）

权威文档：根 `README.md`（网页端完整协议）、`文件汇总20260730/README-IDE.md`（IDE/solo 精简版——本机四个模式都走这一份）。

## 一、IDE 模式下**作废**的规则（别照搬网页端）

`README-IDE.md` 明确声明：复制包接收、旧代码逐字提取、一旧一新对比、发前搜匹配次数——这些属于"AI 拿不到文件、只能靠用户贴代码"的场景，**在能直接读写文件的 IDE 模式下作废**。替代做法：

- 直接 read / glob / grep 定位，不要求用户贴代码；
- 用 edit / write 改，用户看 diff，不输出"旧→新对比"文本；
- 改前确认改动点、影响范围、是否违反铁律；改后跑诊断与验证。

## 二、仍然无条件生效的

- **重构铁律 3 条**：架构不倒退、不兜底、被指出错误先讲清根因再改。
- **迭代铁律 3 条**：主动验证是助手的事（禁止"你去测一下"式交付）；禁止边跑边修、新旧并存；根因确认后一次改透。
- **讨论准则**：先复述理解 → 拿代码原文对齐 → 现象与代码不一致就直接指出 → 一致后再出方案。
- **不确定的规则、数值、设计细节先问，不猜。**
- **信息密度**：每次答复核心信息点 2-4 条，超了就分批；用户说"直接改"则照做。
- **每轮结束报整体完成度**：百分比 + 剩余未完成项清单。
- **诊断走控制台**：特效/动画/位置问题给 F12 脚本，刷新即恢复，不在源文件插临时调试代码。
- **四种协作模式**（`README-IDE.md` 第四节）：普通（默认，详细讨论）／专题（复杂架构或根因不明 Bug，全链路分析 + 控制台诊断）／协助（改动转交另一个 AI）；用户不说 = 普通模式。

## 三、只有用户明确要求"贴代码交付"时才恢复网页端格式

若确实无法直接改文件、必须发文本给人执行，则回到根 `README.md`：旧代码从用户最新原文逐字提取、一组一旧一新、每次 2-4 组默认 3 组、超 3 组先问；完整文件替换必须同步文件头版本号、`export const VER`、预估字节数，且不得省略。

## 四、协助模式（把改动交给别的 Agent 时）

交付提示词必须自带上下文，接收方没读过项目：①任务标题 ②目标与验收标准（列成"验收 N 问"）③只给完成任务必需的背景 ④执行步骤（含文件路径）⑤注意事项（不要动哪些文件、临时脚本跑完删除）。

对方回报后，**你要核实实际 diff / grep / 冒烟结果**，不能照单全收；发现超计划改动如实报给用户决策。
